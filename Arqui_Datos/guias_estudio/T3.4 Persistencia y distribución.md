## 1. Resumen general y objetivos

Este tema aborda cómo Redis —un sistema en memoria— garantiza la **supervivencia de los datos** ante reinicios y fallos, y cómo se escala para soportar alta disponibilidad y grandes volúmenes. Los cinco pilares son: **persistencia** (RDB/AOF/híbrido), **evicción** (qué ocurre cuando la RAM se llena), **replicación** (primary-réplica asíncrona), **Sentinel** (failover automático) y **Cluster** (distribución horizontal con hash slots).

**Resultados de aprendizaje:**
- Comprender las estrategias de persistencia: RDB, AOF y modo híbrido.
- Conocer la arquitectura de replicación primario/réplica.
- Entender Sentinel como sistema de detección de fallos y failover automático.
- Comprender Redis Cluster: hash slots, particionado y redirección MOVED.

La idea central: **Redis no es solo un almacén efímero**. Con RDB+AOF puede sobrevivir a reinicios; con Sentinel puede recuperarse automáticamente de un fallo del nodo primario; con Cluster puede distribuir datos entre cientos de nodos. Cada capa añade disponibilidad pero también complejidad — la clave está en elegir el nivel adecuado al caso de uso.

## 2. Persistencia en Redis

Aunque Redis es un sistema en memoria, ofrece mecanismos de **persistencia** para garantizar la supervivencia de los datos ante reinicios del servidor.

### 2.1 RDB (Redis Database) — Snapshots

RDB crea **snapshots** (instantáneas) periódicas de todo el dataset en un fichero comprimido (`dump.rdb`). El proceso utiliza `fork()` para crear un proceso hijo que escribe el dataset en disco.

**¿Qué es `fork()`?** Es una llamada al sistema operativo que crea una copia del proceso Redis. El proceso hijo ejecuta BGSAVE (escribe el snapshot a disco) mientras el padre sigue sirviendo comandos normalmente. Gracias a **Copy-on-Write (COW)**, la copia es casi instantánea (<1ms) porque solo se copian los metadatos de las páginas, no los datos.

**Copy-on-Write (COW):** el proceso hijo comparte las mismas páginas de memoria con el padre hasta que uno de ellos escribe. Al escribir, el SO crea una copia solo de esa página modificada. Ventaja: el snapshot no bloquea el servidor. Riesgo: si el padre escribe mucho durante el snapshot, la memoria puede duplicarse (cada escritura crea una copia de la página). En producción, monitoriza `INFO memory` durante BGSAVE.

```bash
# redis.conf
save 60 1000    # Snapshot si 1000 keys cambiaron en 60 s
save 300 10     # Snapshot si 10 keys cambiaron en 5 min
save 60 1       # Snapshot si 1 key cambió en 1 min

# Desactivar RDB
save ""

# Guardar manualmente
BGSAVE    # Background save (fork — no bloqueante)
SAVE      # Síncrono (bloquea el servidor — ¡no usar en producción!)
```

| | RDB |
|---|---|
| **Ventajas** | Rápido para backups y restauraciones. Bajo overhead en producción. Buena compatibilidad con réplicas. Formato compacto (fichero comprimido). Ideal para disaster recovery. |
| **Desventajas** | Puede perder datos entre snapshots (últimos N segundos). El fork puede bloquear en datasets grandes (>10 GB). No es ideal para datos críticos por sí solo. El archivo RDB es binario, no legible. |

### 2.2 AOF (Append Only File) — Log de escrituras

AOF registra **cada operación de escritura** en un fichero de log. Es más seguro que RDB pero genera ficheros más grandes.

```bash
# redis.conf
appendonly yes
appendfilename "appendonly.aof"

# Estrategia de sincronización del SO
appendfsync everysec     # Cada segundo (recomendado — balance seguridad/rendimiento)
appendfsync always       # En cada escritura (máxima seguridad — más lento)
appendfsync no           # Dejar que el SO decida (más rápido — menos seguro)

# Reescritura automática del AOF (compactar)
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

| | AOF |
|---|---|
| **Ventajas** | Menor pérdida de datos (máximo 1 segundo con `everysec`). Fichero legible por humanos (formato Redis). Recuperación más granular. No bloquea el servidor durante la escritura normal. |
| **Desventajas** | Ficheros más grandes que RDB. Recuperación más lenta. Mayor overhead en escritura. Reescritura puede causar picos de I/O. |

**Ejemplo real de archivo AOF** (formato RESP legible por humanos):
```
*3
$3
SET
$4
foo
$3
bar
```
Cada línea es un comando Redis. El AOF es un log secuencial de todas las escrituras. Para reconstruir el estado, Redis reproduce los comandos desde el inicio.

### 2.3 Línea temporal de pérdida de datos

```
RDB:     |---snapshot---|---snapshot---|---FAIL---|  → Pierde hasta 15 min (snapshot cada 15 min)
AOF:     |log continuo..............|FAIL|         → Pierde hasta 1s (si fsync everysec)
Híbrido: |log continuo..............|FAIL|         → RDB para backup + AOF para mínimo loss
```

### 2.4 Modo híbrido (recomendado en producción)

Redis 4.0+ permite usar **RDB + AOF simultáneamente**. El AOF se regenera periódicamente a partir del último snapshot RDB.

```bash
# redis.conf
aof-use-rdb-preamble yes    # AOF empieza con snapshot RDB
```

> **Caso real — Twitter:** usa modo híbrido RDB+AOF para sus clústeres Redis. RDB permite backups rápidos (copiar `dump.rdb`), mientras que AOF garantiza que no se pierden más de 1 segundo de datos ante un fallo del servidor.

> **Caso real — GitHub:** usa RDB para snapshots cada 24h (contadores aproximados de stars/forks/watchers) y AOF con `appendfsync everysec` para cada star/fork — en el peor caso, se pierde 1 segundo de datos. Una vez al día, reconstruye los contadores desde MySQL (la fuente de verdad) y los carga en Redis. **Lección:** para contadores aproximados, RDB+AOF es suficiente; no necesitas consistencia perfecta para "cuántas estrellas tiene un repo".

**Resumen T3.4.1:** RDB: snapshots rápidos pero puede perder datos. AOF: log seguro pero fichero grande. Híbrido (recomendado): RDB+AOF. `appendfsync everysec` es el mejor balance.

## 3. Expulsión de datos (Eviction)

Redis es un sistema en memoria: cuando la RAM se llena, expulsa datos según la política configurada (`maxmemory-policy`).

Las 8 políticas de evicción (LRU, LFU, random, TTL, etc.) y sus casos de uso se describen en detalle en T3.3. En esta sección nos centramos en cómo **monitorizar** la evicción en producción.

```bash
INFO memory
# used_memory: 1073741824          (1 GB)
# used_memory_rss: 1157627904      (RAM del SO)
# mem_fragmentation_ratio: 1.08    (fragmentación = rss/used)
# maxmemory: 2147483648            (2 GB)
# maxmemory_policy: allkeys-lru

# Si fragmentation_ratio > 1.5 → hay mucha memoria desperdiciada
# Si used_memory ≈ maxmemory → se están expulsando claves
```

- **`evicted_keys`** (en `INFO stats`): número de claves eliminadas por falta de memoria. Si crece constantemente, necesitas más memoria o un TTL más corto.
- **`mem_fragmentation_ratio`:** si es > 1.5, Redis está desperdiciando RAM (fragmentación). Si < 1, Redis usa swap (muy malo para el rendimiento).

> **Caso real — Twitch:** usa Redis para caché de chat; cuando la memoria se llena, expulsa colores de chat de usuarios inactivos manteniendo los datos más recientes de canales activos.

**Resumen T3.4.2:** `maxmemory` configura el límite. `maxmemory-policy` determina qué se expulsa. Monitoriza `used_memory` y `evicted_keys` con `INFO memory`.

## 4. Replicación en Redis

La replicación en Redis sigue una arquitectura **primary-replica**: un nodo primario recibe todas las escrituras y uno o más réplicas mantienen copias de solo lectura.

```
Cliente (WRITE) → Primary
                  ├── Replicación asíncrona → Réplica 1 (READ)
                  ├── Replicación asíncrona → Réplica 2 (READ)
                  └── Replicación asíncrona → Réplica 3 (READ)
```

### Flujo de replicación (sincronización inicial)

1. El replica se conecta al primary y envía `PSYNC ? -1` (primera conexión).
2. El primary ejecuta `BGSAVE` (fork + COW) y envía el snapshot RDB al replica.
3. Mientras se envía el snapshot, el primary almacena nuevos comandos en un buffer.
4. Una vez enviado el snapshot, el primary envía los comandos del buffer.
5. A partir de ahí, el primary envía cada comando de escritura al replica de forma asíncrona (continuo).

**Ventajas:** Alta disponibilidad, lectura escalable, backup automático.
**Limitaciones:** El primary es el único punto de escritura. La replicación es asíncrona (puede haber lag de milisegundos entre primary y réplicas).

> **Analogía:** El primario es como el original de un documento y las réplicas son las copias. Cada vez que modificas el original, las copias se actualizan. Si el original se pierde, una copia se promueve a original. La diferencia es que en Redis las copias pueden tener un ligero desfase (replicación asíncrona).

> **Caso real — Discord:** usa replicación Redis con factor 3 para garantizar disponibilidad del caché de chat incluso con fallos de nodo. Si el primary falla, uno de los réplicas asume el rol de primary automáticamente.

**Resumen T3.4.3:** Primary-replica asíncrona. El primary escribe, los réplicas leen. Buena disponibilidad pero escritura limitada a un nodo. Factor de replicación 3 = tolerancia a 2 fallos.

## 5. Redis Sentinel

Redis Sentinel es un sistema de **alta disponibilidad** que monitoriza nodos Redis y ejecuta failover automático.

```
Sentinel 1 ─── monitorea ──→ Primary
Sentinel 2 ─── monitorea ──→ Primary    [fallo detectado]
Sentinel 3 ─── monitorea ──→ Primary          ↓
                                    Réplica → Primary (failover)
```

### Proceso de failover automático

1. Un Sentinel detecta que el primary no responde → lo marca como **SDOWN** (Subjectively Down).
2. Los Sentinels se comunican entre sí para confirmar el fallo.
3. Cuando suficientes Sentinels coinciden (quórum) → el primary se marca como **ODOWN** (Objectively Down).
4. Los Sentinels eligen un coordinador (algoritmo Raft).
5. El coordinador selecciona la mejor réplica (por prioridad, offset de replicación, ID) y la promueve a primary.
6. Reconfigura las demás réplicas y notifica a los clientes el nuevo primary.

**Tiempo típico de failover: 10-30 segundos.**

### Conceptos clave

| Concepto | Definición |
|---|---|
| **SDOWN** (Subjective Down) | Un Sentinel individual detecta que el primary no responde tras el timeout. Es subjetivo: puede ser un problema de red del propio Sentinel, no del primary. |
| **ODOWN** (Objective Down) | Múltiples Sentinels coinciden en que el primary está caído, alcanzando el quórum. Es objetivo: el fallo está confirmado por consenso. Solo con ODOWN se inicia el failover. |
| **Quórum** | Número mínimo de Sentinels que deben estar de acuerdo para ejecutar una decisión. Con quórum=2 y 3 Sentinels, al menos 2 deben confirmar el fallo — evita que un Sentinel aislado con problemas de red ejecute un failover fantasma. |
| **Failover** | Proceso automático: (1) Sentinels detectan SDOWN, (2) alcanzan quórum → ODOWN, (3) eligen un Sentinel coordinador, (4) el coordinador selecciona la mejor réplica, (5) la promueve a primary, (6) reconfigura las demás réplicas. |

**Qué verías en los logs durante un failover:**
```
[01] 12:00:01 # +sdown master mymaster 127.0.0.1 6379      ← SDOWN detectado
[01] 12:00:05 # +odown master mymaster 127.0.0.1 6379      ← ODOWN (quórum alcanzado)
[01] 12:00:05 # Failover authentication initiated
[01] 12:00:06 # +failover-state-select-slave               ← Buscando mejor réplica
[01] 12:00:07 # Promoted slave 127.0.0.1:6380              ← Réplica promovida
[01] 12:00:07 # +switch-master mymaster 127.0.0.1 6379     ← Nuevo primary activo
```

> **Caso real — Discord:** usa Redis Sentinel para gestionar instancias de caché de chat con failover automático, consiguiendo disponibilidad del 99,99%.

> «La redundancia no es un gasto, es una inversión en disponibilidad.» — En producción, un sistema sin redundancia es un sistema que fallará. Redis Sentinel y Cluster son tu seguro de vida.

**Resumen T3.4.4:** Sentinel monitoriza nodos y ejecuta failover automático. Mínimo 3 Sentinels para quórum. Detecta SDOWN (subjetivo) → ODOWN (objetivo) → failover.

## 6. Redis Cluster

Redis Cluster permite **distribuir datos entre múltiples nodos** de forma nativa, sin necesidad de proxies externos.

> **Contenido avanzado:** Redis Cluster normalmente lo gestiona un equipo de infraestructura. Para un desarrollador, lo importante es entender que los datos se distribuyen en 16.384 slots y que los clientes inteligentes gestionan las redirecciones automáticamente.

### 6.1 Hash slots y distribución de claves

Redis Cluster divide el espacio de claves en **16.384 hash slots**. Cada nodo es responsable de un rango de slots:

```bash
# Cálculo de hash slots
Slot = CRC16(key) % 16384

# Ejemplo con 3 nodos:
# Nodo A: slots 0 – 5460
# Nodo B: slots 5461 – 10922
# Nodo C: slots 10923 – 16383

SET user:1000 "data"    → CRC16("user:1000") % 16384 = 5461  → Nodo B
SET product:456 "data"  → CRC16("product:456") % 16384 = 12300 → Nodo C
SET session:abc "data"  → CRC16("session:abc") % 16384 = 2000  → Nodo A
```

> **¿Por qué 16.384 slots?** Es un equilibrio: suficiente granularidad para distribuir carga entre hasta 16.384 nodos, pero no tantos que el protocolo sea ineficiente. Con 3 nodos, cada uno tiene aproximadamente 5.461 slots. Con 1.000 nodos, aproximadamente 16 slots cada uno.

### 6.2 Redirección MOVED

Cuando el cliente consulta una clave que está en otro nodo, Redis responde con `-MOVED`:

```bash
-MOVED 5461 192.168.1.2:6379
# El cliente debe reconectar al nodo correcto
# Los clientes inteligentes (Jedis, Lettuce, StackExchange.Redis) gestionan esto automáticamente
```

### 6.3 Gossip Protocol

Redis Cluster usa el protocolo Gossip para que cada nodo conozca el estado de los demás sin un coordinador central. Cada segundo, un nodo envía un PING a un nodo aleatorio con su visión del cluster (qué nodos conoce, qué slots gestiona). El receptor responde con un PONG incluyendo su propia visión. Tras pocas rondas, todos convergen en un estado conocido. Si un nodo no responde tras varios PINGs → marcado como caído.

### 6.4 Resharding en caliente

Redis Cluster permite **mover slots de un nodo a otro sin downtime**. Los slots se migran uno a uno, manteniendo disponibilidad.

**Shard (particionado):** dividir datos entre múltiples instancias Redis, donde cada instancia almacena un subconjunto de claves. En Redis Cluster, las 16.384 hash slots se distribuyen entre los nodos. Si añades un nodo, solo migras algunos slots (no todos los datos).

> **Analogía:** Redis Cluster es como una biblioteca con 3 salas temáticas. Los 16.384 libros (hash slots) se distribuyen entre las salas. Si pides un libro que está en la sala B pero estás en la sala A, te redirigen con un "MOVED". La distribución es automática y balanceada.

> **Caso real — Twitter:** ejecuta uno de los mayores clústeres Redis del mundo. Originalmente usaban Twemproxy (proxy de sharding) para gestionar miles de instancias. Actualmente Redis Cluster nativo es la opción recomendada para nuevos despliegues.

**Resumen T3.4.5:** 16.384 hash slots distribuidos entre nodos. Slot = CRC16(key) % 16384. Resharding en caliente sin downtime. Los clientes gestionan MOVED automáticamente.

## 7. Decisiones de arquitectura

| Pregunta | Cuándo usar Redis | Cuándo NO usar Redis |
|---|---|---|
| ¿Qué datos cachear? | Datos de alta frecuencia de acceso (catálogo, sesiones) | Datos que se escriben más de lo que se leen |
| ¿Cuánta memoria necesito? | Caben en RAM disponible del servidor | No caben en memoria (usar BD en disco) |
| ¿Qué consistencia necesito? | Eventualmente consistente (caché) | Consistencia fuerte (banco de datos) |
| ¿Qué latencia necesito? | Sub-milisegundo | Latencia > 1 ms tolerable |

**Patrón de diseño habitual:** Redis como capa de "hot data" delante de una BD persistente.

> **Caso real — Netflix:** decide qué cachear en EVCache basándose en frecuencia de acceso: catálogo (siempre en caché), perfiles (frecuente), historial completo (nunca en caché).

**Resumen T3.4.6:** Redis para caché de datos calientes, sesiones y contadores. No para datos críticos ni consultas complejas. Redis complementa la BD, no la sustituye.

## 8. Monitorización y operación

### Comando INFO

```bash
INFO server       # versión, uptime, PID
INFO clients      # clientes conectados, bloqueados
INFO memory       # RAM usada, fragmentation ratio, peak memory
INFO persistence  # estado RDB/AOF, operaciones de escritura
INFO stats        # ops/sec, cache hit ratio, keyspace hits/misses
INFO replication  # estado primary/replica, lag
INFO cpu          # uso de CPU del servidor y hijos
```

**Hit rate desde `INFO stats`:**
```bash
keyspace_hits:12345678     ← Lecturas que encontraron la clave
keyspace_misses:234567     ← Lecturas que NO encontraron la clave

# Hit rate = hits / (hits + misses) = 12345678 / (12345678 + 234567) = 98.1%
# Un hit rate >95% es saludable. Si baja de 90%, revisa tu TTL o la memoria disponible.
```

### Métricas clave a monitorizar

| Métrica | Qué indica | Alerta si... |
|---|---|---|
| `connected_clients` | Conexiones activas | > límite configurado |
| `used_memory` | RAM consumida | > 80% de maxmemory |
| `instantaneous_ops_per_sec` | Operaciones/segundo | Pico inesperado |
| `keyspace_hits / misses` | Ratio de acierto de caché | Hit rate < 80% |
| `expired_keys` | Claves expiradas | Muchas expiraciones = TTL bajo |
| `evicted_keys` | Claves expulsadas | > 0 (memoria llena) |
| `latest_fork_usec` | Tiempo de último fork (RDB o reescritura AOF) | > 1 segundo (bloquea el servidor) |

### Comando SLOWLOG

```bash
SLOWLOG GET 10     # Últimas 10 consultas lentas
SLOWLOG LEN        # Número de consultas lentas
SLOWLOG RESET      # Limpiar historial
```

### Herramientas de monitoreo

- **Redis Insight:** GUI oficial para inspeccionar datos y métricas en tiempo real.
- **`redis-cli --latency`:** Mide latencia real del servidor.
- **`redis-cli --bigkeys`:** Encuentra las claves más grandes.
- **`redis-cli --stat`:** Estadísticas en tiempo real.

> **Caso real — GitHub:** usa SLOWLOG para detectar consultas Redis que superan 10 ms y optimizar el patrón de caché en consecuencia. Esto les permite mantener latencia sub-milisegundo en el 99% de las peticiones.

**Resumen T3.4.7:** INFO para métricas del servidor. SLOWLOG para consultas lentas. Redis Insight para GUI. Alerta si: `evicted_keys` > 0, hit rate < 80%, fork > 1s.

## 9. Caso real completo — Discord: Redis para caché de chat

Discord usa Redis para caché de mensajes de chat (colores de nombre, badges, bans) con múltiples instancias particionadas por canal.

**Arquitectura:**
- **Redis:** caché de datos de chat (colores, badges, bans).
- **HAProxy:** balanceo de carga entre instancias Redis.
- **Particionado:** cada canal va a una instancia Redis diferente.

**El problema inesperado:** Discord descubrió que el cuello de botella **no era Redis**, sino el disco. Las escrituras en disco estaban bloqueando las operaciones Redis.

**Solución — "super-disk":**
- **Local SSD RAID0:** escritura rápida en disco local.
- **Persistent Disk RAID1:** replicación para persistencia.

**Lección:** cuando un sistema va lento, el problema no siempre es donde parece. Discord investigó y descubrió que Redis era rápido, pero el disco de persistencia era el cuello de botella. **Medir antes de optimizar.**

## 10. Cuándo aplicar todo esto en la práctica

- Usa RDB + AOF híbrido en producción: RDB para backups rápidos y AOF para mínima pérdida de datos.
- Monitoriza `INFO memory` durante `BGSAVE` para detectar write amplification por copy-on-write.
- Para Sentinel, configura quórum ≥ 2 para evitar failover fantasma por un Sentinel aislado.
- En Redis Cluster, distribuye claves con prefijos consistentes para evitar hotspots en un solo nodo.
- Replica con al menos 3 nodos para tolerar 1 fallo sin perder disponibilidad.
- Para datos críticos, usa replicación + Sentinel (alta disponibilidad) o Cluster (escalabilidad horizontal). Nunca dependas de un solo nodo Redis en producción.

## 11. Preguntas de autoevaluación

**1. ¿Cuál es la diferencia fundamental entre RDB y AOF?**
> RDB crea snapshots periódicos del dataset completo en un fichero binario comprimido (`dump.rdb`) — es rápido para backups pero puede perder los datos escritos entre dos snapshots. AOF registra cada operación de escritura en un log legible por humanos — pierde como máximo 1 segundo de datos (con `appendfsync everysec`) pero genera ficheros más grandes y una recuperación más lenta.

**2. ¿Qué es Copy-on-Write (COW) y por qué permite que BGSAVE no bloquee el servidor?**
> COW es un mecanismo del SO por el que el proceso hijo (creado por `fork()`) comparte las mismas páginas de memoria con el padre. Solo cuando uno de los dos procesos escribe en una página, el SO crea una copia de esa página para el proceso que escribe. Esto permite que el snapshot se tome sin copiar toda la memoria de golpe, por lo que el padre sigue procesando comandos mientras el hijo escribe el snapshot a disco.

**3. ¿Cuándo se recomienda el modo híbrido RDB+AOF y por qué?**
> En producción, siempre. RDB permite backups y restauraciones rápidas, mientras que AOF garantiza una pérdida máxima de 1 segundo de datos. La combinación ofrece lo mejor de ambos: velocidad de backup de RDB y durabilidad de AOF. La opción `aof-use-rdb-preamble yes` hace que el AOF empiece con un snapshot RDB para una recuperación más eficiente.

**4. ¿Qué diferencia hay entre SDOWN y ODOWN en Redis Sentinel?**
> SDOWN (Subjectively Down) es la opinión de un único Sentinel: detecta que el primary no responde tras el timeout, pero puede ser un problema de red del propio Sentinel, no del primary. ODOWN (Objectively Down) es el consenso: múltiples Sentinels han confirmado que el primary está caído, alcanzando el quórum. Solo con ODOWN se inicia el failover automático.

**5. ¿Por qué se necesitan mínimo 3 Sentinels (y no 2)?**
> Para el quórum. Con 2 Sentinels y quórum=2, si uno pierde conectividad de red con el primary (pero el primary está bien), ese Sentinel votará SDOWN pero no podrá alcanzar quórum solo — el failover no se ejecuta. Con 3 Sentinels y quórum=2, dos Sentinels deben estar de acuerdo, lo que evita que un Sentinel aislado con problemas de red ejecute un failover fantasma.

**6. ¿Cómo sabe Redis Cluster a qué nodo enviar una clave?**
> Calculando el hash slot: `Slot = CRC16(key) % 16384`. El cluster tiene 16.384 slots distribuidos entre los nodos. El cliente calcula el slot de la clave y la envía directamente al nodo responsable de ese rango. Si el cliente se equivoca de nodo, este responde con `-MOVED <slot> <ip:port>` y el cliente redirige automáticamente.

**7. ¿Qué es el Gossip Protocol en Redis Cluster y para qué sirve?**
> Es el protocolo de comunicación peer-to-peer entre nodos del cluster. Cada segundo, cada nodo envía un PING a un nodo aleatorio con su visión del estado del cluster. El receptor responde con PONG incluyendo su propia visión. Tras pocas rondas, todos los nodos convergen en un estado conocido sin necesidad de un coordinador central.

**8. ¿Qué significa `mem_fragmentation_ratio` y cuándo es un problema?**
> Es el ratio entre la RAM del SO (`used_memory_rss`) y la RAM que Redis cree que usa (`used_memory`). Un ratio > 1.5 indica mucha fragmentación de memoria (Redis pide más RAM al SO de la que realmente usa). Un ratio < 1 indica que Redis usa swap, lo cual es muy malo para el rendimiento (swap en disco es órdenes de magnitud más lento que RAM).

**9. ¿Qué hace `evicted_keys` y cuándo deberías preocuparte?**
> `evicted_keys` (en `INFO stats`) muestra el número de claves eliminadas por falta de memoria (por la política `maxmemory-policy`). Si este valor crece constantemente, Redis está activamente expulsando datos para hacer espacio — significa que la caché está llena y se está perdiendo información. La solución es aumentar `maxmemory`, añadir más RAM, reducir TTLs o revisar la política de evicción.

**10. ¿Cuándo elegirías Sentinel y cuándo Redis Cluster?**
> Sentinel es para **alta disponibilidad** con un único shard: detecta caídas del primary y hace failover automático en 10-30 segundos. Es suficiente cuando los datos caben en un solo nodo. Redis Cluster es para **escalabilidad horizontal**: cuando los datos no caben en un solo nodo o la carga de escritura supera la capacidad de un único primary. Cluster incluye replicación y failover nativo, por lo que en escalas muy grandes reemplaza a Sentinel.

**11. Si Redis usa `fork()` en un dataset de 50 GB, ¿qué problema de latencia podrías experimentar?**
> En datasets grandes (>10 GB), el `fork()` puede causar un pico de latencia porque copia la tabla de páginas completa. Además, si el proceso padre escribe mucho durante el snapshot (COW activo), la memoria puede duplicarse temporalmente. Para evitarlo: usar instancias más pequeñas con Redis Cluster (distribuye el dataset entre varios nodos reduciendo el tamaño de cada snapshot) o planificar BGSAVE en horas de baja carga.

**12. ¿Qué diferencia hay entre Sentinel (alta disponibilidad) y Cluster (escalabilidad)?**
> Sentinel resuelve el problema de **disponibilidad** con un único shard: si el primary cae, promueve automáticamente una réplica, con downtime de 10-30 segundos. Cluster resuelve el problema de **escala**: distribuye los datos en múltiples shards (grupos primary+réplicas), cada uno responsable de un rango de hash slots. Cluster incluye failover automático por shard, por lo que a gran escala combina disponibilidad y escalabilidad sin necesidad de Sentinel externo.
