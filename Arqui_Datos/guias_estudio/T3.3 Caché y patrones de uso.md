## 1. Resumen general y objetivos

Este tema cierra el bloque de Redis centrándose en su uso más extendido en la industria: **la caché**. No basta con saber que Redis es rápido — hay que entender *por qué* lo es (comparativa de latencias), *cómo* se integra una caché con la base de datos principal (las cuatro estrategias: Cache-Aside, Write-Through, Write-Behind, Read-Through), *cómo* se mantiene sincronizada con los datos reales (invalidación, TTL, el problema del *thundering herd*), *qué* pasa cuando la memoria se llena (políticas de expulsión LRU/LFU) y, finalmente, cómo se combinan estas piezas en **patrones prácticos** reales (sesiones, caché de productos, rate limiting).

**Resultados de aprendizaje:**
- Comprender los conceptos de caché, TTL y expulsión de datos.
- Conocer las estrategias de caché: Cache-Aside, Write-Through, Write-Behind, Read-Through.
- Entender el problema del *thundering herd* y cómo mitigarlo con `SETNX`.
- Aplicar patrones prácticos: sesiones, rate limiting, rankings con Sorted Sets.

La idea central del tema: **una caché no es solo "guardar cosas para que vayan más rápido"**. Es una decisión de ingeniería con trade-offs explícitos entre consistencia, rendimiento de escritura, complejidad de implementación y riesgo de pérdida de datos. Elegir mal la estrategia, olvidar el TTL, o no proteger la caché de un *thundering herd* son errores que a pequeña escala no se notan, pero que revientan un sistema en producción.

## 2. Concepto de caché

Una **caché** es un almacén de datos de acceso rápido que guarda copias de datos consultados frecuentemente, con el objetivo de **reducir la latencia** y **la carga sobre el sistema de almacenamiento principal** (típicamente una base de datos en disco).

### Latencia comparada (por qué Redis funciona como caché)

| Medio | Latencia típica | Factor relativo | Ejemplo |
|---|---|---|---|
| CPU L1 cache | ~0,5 ns | 1× | Registro del procesador |
| CPU L2 cache | ~7 ns | 14× | Caché del núcleo |
| RAM (Redis) | ~100 ns (0,1 µs) | 200× | Almacenamiento principal |
| SSD | ~100 µs (0,1 ms) | 200 000× | Disco de estado sólido |
| Red (localhost) | ~500 µs (0,5 ms) | 1 000 000× | Mismo servidor |
| Red (cross-region) | ~50–100 ms | 100 000 000× | US-EU |

**Idea clave:** Redis en memoria es **1.000 veces más rápido que SSD** y **100 millones de veces más rápido que una petición cross-region**. Esta diferencia de órdenes de magnitud —no solo "un poco más rápido"— es la razón de fondo por la que una caché en memoria delante de una base de datos en disco tiene sentido económico y técnico.

### Flujo de una petición con caché

```
Petición del cliente
        │
        ▼
   ¿Está en caché?
   ├── Sí (hit)  → Devolver dato de caché
   └── No (miss) → Consultar BD principal
                    → Almacenar en caché con TTL
                    → Devolver dato de caché
        │
        ▼
  Respuesta al cliente
```

### Métricas clave de caché

- **Hit rate (tasa de acierto):** porcentaje de peticiones resueltas desde caché. Un hit rate del 95% significa que solo el 5% de las peticiones llegan a la BD.
- **Miss rate (tasa de fallo):** porcentaje de peticiones que necesitan consultar la BD (= 100% − hit rate).
- **TTL medio:** tiempo promedio que un dato permanece en caché antes de expirar.

> **Caso real — Netflix (EVCache):** consigue latencia sub-milisegundo para el 99% de las peticiones de catálogo, reduciendo las llamadas a Cassandra en un 95%. Su hit rate promedio supera el 99%, es decir, solo 1 de cada 100 peticiones necesita ir a la base de datos.

**Resumen T3.3.1:** Redis en RAM es 1.000× más rápido que SSD. Un hit rate del 95% significa que solo el 5% de las peticiones llega a la BD. El objetivo de la caché es maximizar aciertos y minimizar consultas a la BD.

## 3. Estrategias de caché

Existen cuatro estrategias fundamentales para integrar una caché con el sistema de almacenamiento principal. Se diferencian en **quién** hace cada operación (la aplicación o la propia caché) y **cuándo** se sincronizan caché y BD.

### 3.1 Cache-Aside (Lazy Loading) — la más común

La aplicación es responsable de gestionar la caché explícitamente:

1. La aplicación pide el dato a Redis (`GET clave`).
2. **Hit:** Redis lo tiene → se devuelve directamente.
3. **Miss:** Redis no lo tiene → la aplicación consulta MariaDB → guarda el resultado en Redis con TTL (`SET clave dato TTL`) → devuelve el dato.

**Ventaja:** solo se carga en caché lo que realmente se necesita. **Desventaja:** en caso de fallo hay **tres accesos** (GET a Redis, SELECT a BD, SET a Redis) — el conocido *cache miss penalty*.

> **Analogía — La farmacia:** la estantería de la farmacia es la caché (acceso rápido, pocos productos, siempre los más demandados); el almacén del distribuidor es la base de datos (tiene todo, pero tarda más en llegar).
> 1. **Hit:** el farmacéutico busca en la estantería → lo tiene → te lo da en 5 segundos.
> 2. **Miss:** no lo tiene → llama al distribuidor (BD) → lo recibe → lo pone en la estantería (`SET`) con fecha de caducidad (TTL) → te lo da.
> 3. **Próxima vez:** otro cliente pide lo mismo → ya está en la estantería (hit).
>
> ¿Por qué no guardar *todo* en la estantería? Porque es **pequeña y cara** (RAM). Solo se guarda lo que se consulta frecuentemente; si un producto lleva mucho tiempo sin consultarse, se retira (evicción por TTL o LRU, ver sección 5).

```csharp
// C# — Cache-Aside con StackExchange.Redis
using StackExchange.Redis;
using System.Text.Json;

var mux = await ConnectionMultiplexer.ConnectAsync("localhost");
var db = mux.GetDatabase();

async Task<Producto?> GetProductoAsync(int id)
{
    var key = $"producto:{id}";
    var cached = await db.StringGetAsync(key);

    if (!cached.IsNullOrEmpty)
        return JsonSerializer.Deserialize<Producto>(cached!);

    // Cache miss — consultar BD
    var producto = await _db.Productos.FindAsync(id);
    if (producto != null)
    {
        var json = JsonSerializer.Serialize(producto);
        await db.StringSetAsync(key, json, TimeSpan.FromMinutes(30));
    }
    return producto;
}
```

```python
# Python — Cache-Aside con redis-py
import redis, json

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

def get_producto(producto_id: int) -> dict | None:
    key = f"producto:{producto_id}"
    cached = r.get(key)

    if cached:
        return json.loads(cached)

    # Cache miss — consultar BD
    producto = db.query("SELECT * FROM productos WHERE id = %s", producto_id)
    if producto:
        r.setex(key, 1800, json.dumps(producto))  # TTL 30 min
    return producto
```

### 3.2 Write-Through

La aplicación escribe **siempre** primero en Redis, y es Redis quien propaga el escrito a MariaDB de forma síncrona antes de confirmar la operación: `Aplicación → SET → Redis → INSERT/UPDATE → MariaDB → OK → OK`.

**Ventaja:** consistencia garantizada (caché y BD siempre sincronizadas). **Desventaja:** escritura más lenta (dos operaciones secuenciales antes de responder al cliente).

### 3.3 Write-Behind (Write-Back)

La aplicación escribe en Redis, que responde `OK` **inmediatamente** (rápido), y de forma asíncrona encola la escritura hacia MariaDB a través de una cola (batch `INSERT`/`UPDATE`): `Aplicación → SET → Redis → OK (rápido)` + `Redis → Encolar escritura → Cola → Batch INSERT/UPDATE → MariaDB`.

**Ventaja:** escritura muy rápida (un solo write inmediato). **Desventaja:** riesgo de pérdida de datos si falla la cola antes de persistir en BD.

> **Caso real — Instagram:** usa Write-Behind para los "me gusta": incrementa en Redis al instante (`INCR post_likes:{post_id}`) y persiste en Cassandra de forma asíncrona. El usuario ve el like instantáneamente, y Cassandra se actualiza unos milisegundos después.

### 3.4 Read-Through (lectura a través de caché)

La **caché** gestiona la carga desde la BD, no la aplicación. La aplicación solo habla con Redis; si Redis no tiene el dato, es la propia caché quien lo carga desde MariaDB:

```
# 1. Aplicación consulta Redis
GET product:456:info
# → (nil)  (cache miss)

# 2. Redis internamente consulta MariaDB
# SELECT * FROM products WHERE id=456
# → {name: "Laptop Pro", price: 1299}

# 3. Redis almacena y devuelve el resultado
# SET product:456:info '{"name":"Laptop Pro","price":1299}' EX 300
# → '{"name": "Laptop Pro", "price": 1299}'

# 4. Siguientes consultas son cache hit
GET product:456:info
# → '{"name": "Laptop Pro", "price": 1299}'  (0.5ms vs 50ms)
```

**Read-Through vs Cache-Aside:** la diferencia es **quién carga el dato desde la BD**. En Cache-Aside lo hace la aplicación; en Read-Through lo hace la propia caché. Read-Through simplifica el código de la aplicación, pero requiere una capa de caché "inteligente" — Redis no lo hace nativamente, se implementa con *scripts* Lua (que ejecutan `GET` + *fallback* a BD en un solo *roundtrip*) o módulos.

### Comparativa de estrategias

| Estrategia | Consistencia | Rendimiento escritura | Complejidad | Cuándo usar |
|---|---|---|---|---|
| **Cache-Aside** | Eventual | Media | Baja | Caché general, datos que se leen más de lo que se escriben |
| **Write-Through** | Fuerte | Baja (2 writes) | Media | Datos críticos que necesitan consistencia inmediata |
| **Write-Behind** | Eventual | Muy alta (1 write) | Alta | Métricas, likes, eventos de alta frecuencia donde la pérdida temporal es aceptable |
| **Read-Through** | Eventual | Media | Media | Cuando la caché gestiona la carga automáticamente (no la aplicación) |

**En la práctica:** el **80% de los casos** usan Cache-Aside por su simplicidad. Write-Behind es ideal para métricas de alta frecuencia (Instagram likes). Write-Through es raro en la práctica porque dobla el coste de escritura.

**Resumen T3.3.2:** Cache-Aside (80% de casos), Write-Through (consistencia fuerte), Write-Behind (máxima velocidad), Read-Through (caché gestiona la carga). Se elige según la necesidad de consistencia y rendimiento.

## 4. Invalidación de caché

> «La invalidación de caché es uno de los dos problemas difíciles de la informática.» — Phil Karlton

El **objetivo** de la invalidación es mantener la caché sincronizada con la base de datos. Existen dos mecanismos complementarios:

### 4.1 Expiración por tiempo (TTL)

```bash
# TTL en segundos
SET cache:product:456 "iPhone" EX 300     # 5 minutos

# TTL en milisegundos
SET cache:session:abc "data" PX 1800000   # 30 minutos

# Añadir TTL a clave existente
EXPIRE cache:product:456 600              # 10 minutos

# Verificar TTL restante
TTL cache:product:456   # -1 = sin expiración, -2 = no existe, >0 = segundos
```

### 4.2 Invalidación por evento

Cuando el dato de origen cambia, se invalida (o actualiza) la caché de forma explícita:

```bash
# 1. Actualizar MariaDB
# UPDATE products SET price=29.99 WHERE id=456;

# 2. Invalidar caché en Redis
DEL cache:product:456

# 3. Opcionalmente, pre-cargar el nuevo valor
SET cache:product:456 '{"name":"iPhone","price":29.99}' EX 300
```

### 4.3 Problemas comunes

- **Caché obsoleta (*stale cache*):** el dato en caché está desactualizado respecto a la BD. Solución: TTL corto o invalidación por evento.
- **Efecto de multitud (*thundering herd*):** cuando expira una clave popular, múltiples clientes consultan la BD simultáneamente, saturándola. Solución: locks o TTL desfasados.
- **Caché rota (*cache stampede*):** variante del *thundering herd* donde muchos clientes intentan regenerar la caché al mismo tiempo.

### 4.4 Solución al thundering herd: SETNX lock + jitter

```bash
# PROBLEMA: 1000 clientes piden product:456 al mismo tiempo
# El TTL expira → 1000 consultas simultáneas a MariaDB

# SOLUCIÓN 1: Lock con SETNX (solo 1 cliente carga el dato)
# Cliente 1: intenta adquirir el lock
SET lock:product:456 "loading" NX EX 10
# → OK  (adquirió el lock)

# Clientes 2-1000: intentan adquirir el lock
SET lock:product:456 "loading" NX EX 10
# → (nil)  (no adquirieron el lock)

# Cliente 1: carga el dato desde MariaDB
SELECT * FROM products WHERE id=456
# → {name: "Laptop Pro", price: 1299}

# Cliente 1: almacena el dato Y libera el lock
SET product:456:info '{"name":"Laptop Pro","price":1299}' EX 300
DEL lock:product:456

# Clientes 2-1000: ahora encuentran el dato en caché
GET product:456:info
# → {'name': 'Laptop Pro', 'price': 1299}  ✅

# SOLUCIÓN 2: TTL desfasado (jitter)
# En lugar de EX 300, usa EX random entre 270-330
SET product:456:info '{"name":"Laptop Pro"}' EX $((RANDOM % 60 + 270))
# Los TTLs de diferentes clientes no expiran todos a la vez
```

**`SETNX` + `EX`:** `SET key value NX EX seconds` es atómico — solo un cliente obtendrá `OK`. Los demás esperan o leen de caché (si ya se cargó).

**Jitter** = aleatorización intencional de un valor para evitar sincronización no deseada. Si 1.000 claves tienen `TTL=3600`, añadir jitter de ±10% (360-3960s) evita que todas expiren al mismo tiempo. Sin jitter: 1.000 claves expiran simultáneamente → 1.000 queries a la BD de golpe (*thundering herd*). Con jitter, las expiraciones se distribuyen a lo largo de ~6 minutos.

> **Caso real — Twitter:** invalida timelines en Redis cuando un usuario borra un tweet, usando eventos de Kafka para notificar a todas las réplicas en tiempo real. El proceso es: 1) el tweet se borra de Cassandra, 2) se publica un evento en Kafka, 3) todos los *consumers* de Kafka borran el tweet de los timelines en Redis.

**Invalidación vs Evicción (matiz importante):** son dos problemas distintos del mismo contexto. La **invalidación** resuelve el problema de **consistencia**: ¿cómo mantengo la caché sincronizada cuando los datos originales cambian? La **evicción** (sección 5) resuelve el problema de **memoria**: ¿qué hago cuando la caché se llena y necesito espacio para nuevos datos? En la práctica ambos se gestionan juntos: se define un TTL para invalidar por tiempo, y una política de evicción para gestionar la memoria.

**Resumen T3.3.3:** TTL para expiración por tiempo. Invalidación por evento (`DEL`) cuando cambia la BD. Cuidado con el efecto de multitud (*thundering herd*) al expirar claves populares — se mitiga con `SETNX` (lock) o jitter (TTL desfasado).

## 5. Políticas de expulsión (Eviction)

Cuando la memoria de Redis se llena, necesita **expulsar** claves para liberar espacio. Las políticas de expulsión determinan qué claves se eliminan.

> **Contenido avanzado:** las políticas de evicción son importantes para producción, pero para entender los conceptos básicos de caché basta con centrarse en `allkeys-lru` (la más habitual) y `noeviction`.

- **LRU (Least Recently Used):** elimina el dato que hace más tiempo se usó. Siendo `access_time` la última vez que se leyó/escribió la clave, LRU elimina la clave con `access_time` más antiguo. Simple, pero puede eliminar datos que se usan regularmente si hubo un pico de tráfico puntual.
- **LFU (Least Frequently Used):** elimina el dato que menos veces se ha usado en una ventana de tiempo reciente. Redis usa un contador aproximado (no exacto) para evitar *overhead* de memoria. Más preciso que LRU para cachés con patrones de uso variables.

### Tabla de políticas

| Política | Descripción | Cuándo usar |
|---|---|---|
| `noeviction` | Error cuando la memoria está llena | Datos críticos donde perder datos es inaceptable. Redis devuelve error en escrituras |
| `allkeys-lru` | Least Recently Used en todas las claves | Caché general de API (cache-aside). No importa qué clave se elimina, solo mantener las más recientes |
| `volatile-lru` | LRU solo en claves con TTL | Sesiones de usuario con TTL. Los datos sin TTL (configuración permanente) nunca se eliminan |
| `allkeys-lfu` | Least Frequently Used | Caché de productos donde los más vendidos deben permanecer más tiempo |
| `volatile-lfu` | LFU solo en claves con TTL | Similar a `volatile-lru` pero por frecuencia |
| `volatile-ttl` | Expulsa claves con TTL más corto | Datos con diferentes niveles de frescura: elimina los que caducan antes |
| `allkeys-random` | Expulsión aleatoria | Cuando todos los datos son igual de importantes |
| `volatile-random` | Aleatorio solo en claves con TTL | Similar a `allkeys-random` pero con TTL |

```conf
# En redis.conf
maxmemory 2gb
maxmemory-policy allkeys-lru

# O en tiempo de ejecución
CONFIG SET maxmemory 2gb
CONFIG SET maxmemory-policy allkeys-lru

# Verificar configuración actual
CONFIG GET maxmemory
CONFIG GET maxmemory-policy
```

> «Lo que mides, lo gestionas.» — Peter Drucker. Monitoriza siempre la tasa de aciertos de caché (*hit rate*). Si cae por debajo del 80%, es hora de reconsiderar la estrategia de caché.

**Producción:** configura siempre `maxmemory-policy allkeys-lru` en producción. Sin esta configuración, Redis devolverá errores cuando la memoria se llene en lugar de expulsar claves antiguas (comportamiento por defecto: `noeviction`).

> **Caso real — GitHub:** usa `volatile-lru` para expulsar sesiones antiguas mientras mantiene en caché las claves de *rate limiting* que no tienen TTL. Las sesiones tienen TTL (30 min), pero los contadores de rate limiting no (se resetean por timestamp), por lo que `volatile-lru` solo expulsa las sesiones.

**Resumen T3.3.4:** `allkeys-lru` es la política más habitual. `volatile-lru` solo expulsa claves con TTL. `noeviction` genera error si la memoria se llena. Configura `maxmemory` según tu presupuesto de RAM.

## 6. Patrones prácticos de caché

### Patrón 1: Sesión de usuario

```bash
# Crear sesión tras login
SET session:abc123:userId "1000" EX 1800
SET session:abc123:role "admin" EX 1800
SET session:abc123:lastAccess "2026-09-15T10:30:00" EX 1800

# Verificar sesión en cada petición
GET session:abc123:userId

# Renovar sesión (sliding expiration)
EXPIRE session:abc123:userId 1800

# Cerrar sesión (logout)
DEL session:abc123:userId
DEL session:abc123:role
DEL session:abc123:lastAccess
```

### Patrón 2: Caché de producto (Cache-Aside)

```bash
# Flujo de lectura (pseudocódigo de la aplicación):
# 1. value = redis.GET("product:456:info")
# 2. if value == null:
# 3.     data = db.query("SELECT * FROM products WHERE id=456")
# 4.     redis.SET("product:456:info", data, EX=300)
# 5.     return data
# 6. return value

# Invalidar cuando se actualiza
# UPDATE products SET price=29.99 WHERE id=456;
DEL product:456:info
```

### Patrón 3: Rate limiting con ventana deslizante

```bash
# Registrar petición
ZADD ratelimit:user:1000 1726400000 "req-001"

# Eliminar peticiones fuera de la ventana (última hora)
ZREMRANGEBYSCORE ratelimit:user:1000 0 1726396400

# Contar peticiones en la ventana actual
ZCARD ratelimit:user:1000

# Si ZCARD > 100 → rechazar la petición (HTTP 429)
```

> **Twitch:** como se vio en T3.1, Twitch Plays Pokémon recibió 1,2 millones de mensajes en 24 horas y la solución fue *shard* por canal de chat.

**Resumen T3.3.5:** sesiones con TTL. Cache-Aside para productos. Rate limiting con Sorted Sets y ventana deslizante. Patrones que cubren el 90% de casos de uso reales.

### Caso real completo — GitHub: Rate Limiting con Sorted Sets

GitHub necesita *rate limiting* con **5.000 peticiones/hora** por usuario autenticado. La solución usa Redis con Sorted Sets para garantizar atomicidad sin necesidad de *scripts* de servidor.

**¿Por qué Sorted Sets y no `INCR`?** `INCR` + `EXPIRE` son dos comandos separados y no son atómicos juntos. Si el cliente muere entre ambos, la clave queda sin TTL. `ZADD` es atómico por diseño: cada petición se registra de forma segura con su propio timestamp como *score*.

```csharp
// C# — Rate limiting con Sorted Sets
var key = $"ratelimit:user:{userId}";
var now = DateTimeOffset.UtcNow.ToUnixTimeSeconds();
var windowStart = now - 3600; // ventana de 1 hora

// ZADD es atómico: registra cada petición
await db.SortedSetAddAsync(key, now, $"{now}:{Guid.NewGuid()}");

// Eliminar peticiones fuera de ventana
await db.SortedSetRemoveRangeByScoreAsync(key, 0, windowStart);

// Contar peticiones en ventana actual
var count = await db.SortedSetLengthAsync(key);

if (count > 5000)
{
    return Results.StatusCode(429); // Too Many Requests
}
```

**Arquitectura en producción:**
- **Sharding client-side:** cada instancia de la aplicación elige qué clúster Redis usar.
- **Primary + réplicas:** *primary* para escrituras, réplicas para lecturas de verificación.
- **Feature flags:** migración gradual de un sistema de rate limiting a otro.

**Lección:** en producción, la atomicidad de las operaciones Redis es crítica. `ZADD` garantiza que dos peticiones concurrentes del mismo usuario nunca se pierdan, sin necesidad de transacciones complejas.

### Caso real completo — Netflix: EVCache

Netflix usa **EVCache**, un sistema de caché distribuido basado en Memcached/Redis, para servir contenido a más de 230 millones de suscriptores en todo el mundo.

| Caso | Descripción |
|---|---|
| **Lookaside Cache** | Aplicación → EVCache → Cassandra (fallback). Consulta caché primero; si falla, consulta Cassandra |
| **Datos transitorios** | Sesiones de reproducción entre microservicios. Se borran automáticamente al cerrar sesión |
| **Pre-cómputo** | Homepage personalizada calculada cada noche, servida desde caché |
| **Alto volumen** | Strings de UI e idiomas. Alta disponibilidad, baja latencia |

**Arquitectura:**
- **Multi-región:** caché por continente para minimizar latencia.
- **Fallback automático:** si la caché falla, lectura directa de Cassandra.
- **Latencia:** sub-milisegundo para el 99% de peticiones de catálogo.

**Lección:** Redis no funciona solo. En sistemas globales como Netflix, Redis/EVCache se integra con bases de datos como Cassandra en una arquitectura de múltiples capas con *fallback* automático.

## 7. Cuándo aplicar todo esto en la práctica

- Siempre define TTL — una caché sin TTL es una bomba de memoria que acabará expulsando datos útiles sin control.
- Mide tu *hit rate* con `INFO keyspace` antes de optimizar; no asumas que la caché funciona bien.
- Para Write-Behind, considera **Redis Streams** como cola de escritura asíncrona a la BD.
- En caché de sesiones, usa `SETEX` (SET + EXPIRE atómico) para evitar claves sin TTL por errores de la aplicación.
- Para datos críticos (precio, stock), la invalidación manual con `DEL` es más fiable que depender solo del TTL.
- Si detectas una clave "caliente" con muchísimo tráfico, combina TTL desfasado (jitter) y/o un lock con `SETNX` para evitar el *thundering herd*.

## 8. Preguntas de autoevaluación

**1. ¿Por qué Redis en memoria es tan efectivo como caché delante de una base de datos en disco?**
> Porque la diferencia de latencia es de varios órdenes de magnitud: RAM (~100 ns) es ~1.000 veces más rápida que SSD (~100 µs) y ~100 millones de veces más rápida que una petición cross-region. Esa brecha, no una simple mejora incremental, es lo que justifica la caché.

**2. ¿Qué es el *cache miss penalty* en Cache-Aside y por qué ocurre?**
> Es el coste de un fallo de caché: hacen falta **tres accesos** en lugar de uno — `GET` a Redis (falla), `SELECT` a la BD, y `SET` de vuelta a Redis — antes de poder devolver el dato al cliente.

**3. ¿Cuál es la diferencia fundamental entre Write-Through y Write-Behind?**
> Write-Through escribe de forma **síncrona** en la BD antes de confirmar la operación al cliente (consistencia fuerte, escritura más lenta). Write-Behind confirma la escritura al cliente inmediatamente tras escribir en Redis, y persiste en la BD de forma **asíncrona** vía una cola (escritura muy rápida, con riesgo de pérdida de datos si la cola falla).

**4. ¿Por qué Instagram usa Write-Behind para los "me gusta" y no Write-Through?**
> Porque necesita máxima velocidad de escritura (millones de likes/día) y puede tolerar la pérdida temporal de unos pocos likes si el sistema falla justo antes de persistir en Cassandra — el impacto de esa pérdida es mínimo comparado con el coste de duplicar cada escritura de forma síncrona.

**5. ¿En qué se diferencia Read-Through de Cache-Aside?**
> En quién carga el dato desde la BD tras un fallo de caché. En Cache-Aside lo hace la aplicación (lógica explícita en el código). En Read-Through lo hace la propia caché de forma transparente — la aplicación solo habla con Redis, y este consulta la BD internamente (normalmente vía scripts Lua, ya que Redis no lo soporta de forma nativa).

**6. Explica el problema del *thundering herd* y dos formas de mitigarlo.**
> Ocurre cuando expira una clave muy consultada y cientos o miles de clientes consultan simultáneamente la BD para regenerarla, saturándola. Se mitiga con: (1) un **lock** con `SETNX ... NX EX` para que solo un cliente cargue el dato mientras el resto espera o lee la caché ya regenerada, o (2) **jitter**: aleatorizar el TTL de claves similares para que no expiren todas a la vez.

**7. ¿Por qué `SET lock:clave "loading" NX EX 10` resuelve el thundering herd y `SET lock:clave "loading" EX 10` (sin `NX`) no lo haría?**
> `NX` (*not exists*) garantiza que la operación solo tiene éxito si la clave no existía — es una operación atómica de "adquisición de lock": solo un cliente obtiene `OK`, el resto recibe `(nil)`. Sin `NX`, todos los clientes sobrescribirían la clave indistintamente y todos "creerían" tener el lock, sin ninguna exclusión real.

**8. ¿Cuál es la diferencia entre invalidación y evicción de caché?**
> La invalidación resuelve un problema de **consistencia**: mantener la caché sincronizada con los datos reales cuando estos cambian (TTL, `DEL` por evento). La evicción resuelve un problema de **memoria**: qué claves eliminar cuando la caché se llena y hace falta espacio para datos nuevos (políticas LRU/LFU). Son problemas distintos que en la práctica se gestionan de forma conjunta.

**9. ¿Qué diferencia hay entre las políticas `allkeys-lru` y `volatile-lru`?**
> `allkeys-lru` puede expulsar cualquier clave de la base de datos, tenga o no TTL configurado. `volatile-lru` solo expulsa claves que tienen TTL asignado; las claves sin TTL (consideradas permanentes/de configuración) nunca se eliminan por esta política, aunque la memoria esté llena.

**10. Si no configuras `maxmemory-policy`, ¿qué ocurre cuando Redis se queda sin memoria?**
> Se aplica la política por defecto, `noeviction`, que hace que Redis **devuelva error** en las operaciones de escritura en lugar de expulsar claves antiguas automáticamente. Por eso en producción se recomienda configurar explícitamente `allkeys-lru` (u otra política adecuada al caso de uso).

**11. ¿Por qué GitHub usa Sorted Sets (`ZADD`) en lugar de `INCR` + `EXPIRE` para su rate limiting?**
> Porque `INCR` y `EXPIRE` son dos comandos separados y no son atómicos entre sí: si el cliente falla justo entre ambos, la clave del contador queda sin TTL (fuga de memoria y comportamiento incorrecto). `ZADD` registra cada petición como una operación atómica única, sin depender de una segunda llamada para fijar la expiración.

**12. Describe el patrón de rate limiting con ventana deslizante usando Sorted Sets.**
> Cada petición se añade con `ZADD` usando el timestamp como *score*. Antes de contar, se eliminan con `ZREMRANGEBYSCORE` las entradas anteriores al inicio de la ventana (p. ej. hace más de una hora). Después se cuenta con `ZCARD`; si el resultado supera el límite permitido, se rechaza la petición (HTTP 429). A diferencia de una ventana fija con `INCR`+`EXPIRE`, esta ventana es continua/deslizante, no se reinicia de golpe cada hora.

**13. ¿Qué significa que la caché de Netflix (EVCache) tenga *fallback* automático a Cassandra?**
> Que si la consulta a la caché falla o no encuentra el dato, el sistema recurre automáticamente a Cassandra como fuente de verdad, sin que la aplicación tenga que gestionar ese caso especial manualmente. Es el patrón *Lookaside Cache*: Aplicación → EVCache → Cassandra (solo si EVCache falla o no tiene el dato).

**14. ¿Por qué se recomienda usar `SETEX` en lugar de `SET` seguido de `EXPIRE` al crear una sesión?**
> Porque `SETEX clave TTL valor` combina `SET` y `EXPIRE` en una única operación atómica. Si se hicieran por separado (`SET` y luego `EXPIRE`), un fallo de la aplicación entre ambas llamadas dejaría una clave de sesión sin TTL — un riesgo de fuga de memoria y de sesiones que nunca expiran.

**15. Un ranking de videojuego necesita mostrar el top 10 en tiempo real y también servir de caché ante caídas de la BD principal. ¿Qué combinación de conceptos de este tema aplicarías y por qué?**
> Una **Sorted Set** para el ranking (visto en T3.2, aquí aplicado como patrón práctico), con estrategia **Cache-Aside** para poblarlo desde la BD si Redis se reinicia, un **TTL** razonable o invalidación por evento cuando cambian las puntuaciones, y una política de expulsión `allkeys-lru`/`volatile-lru` si el ranking convive con otros datos en la misma instancia y la memoria es limitada. La combinación de patrones —no una única estructura— es lo que resuelve el caso de uso completo.
