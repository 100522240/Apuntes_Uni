## 1. Resumen general y objetivos

Este tema profundiza en las **cinco estructuras de datos principales de Redis** (Strings, Hashes, Lists, Sets y Sorted Sets), en cómo elegir la más adecuada según el problema, y en el patrón de modelado **embeber vs referenciar**. Se apoya en casos reales (Twitter, Instagram, GitHub, Netflix) para mostrar cómo empresas con tráfico masivo modelan sus datos en Redis, y cierra con una introducción a los **Redis Modules** (RediSearch, RedisJSON, RedisTimeSeries, RedisBloom), que amplían Redis más allá del clave-valor puro.

**Resultados de aprendizaje:**
- Conocer las 5 estructuras principales de Redis y cuándo usar cada una.
- Saber elegir la estructura adecuada según el caso de uso real.
- Comprender el patrón *embeber vs referenciar* y cuándo aplicar cada opción.
- Explorar módulos avanzados como RediSearch y RedisJSON.

La idea central del tema es que **en Redis no existe "la" estructura correcta**: cada una está optimizada para un patrón de acceso concreto (lectura por clave completa, acceso a un campo, cola FIFO/LIFO, pertenencia a un conjunto, ranking ordenado...). Elegir mal la estructura no rompe la aplicación, pero sí el rendimiento y el consumo de memoria a escala.

## 2. ¿Qué estructura de datos uso? (mapa de decisión)

Antes de memorizar comandos, hay que interiorizar el criterio de decisión. Redis no impone un esquema: el modelador elige la estructura en función de **cómo se va a leer y escribir el dato**, no solo de qué forma tiene.

| Necesidad | Estructura | Ejemplo | Por qué |
|---|---|---|---|
| Valor simple con expiración (TTL) | String | `SET cache:product:456 "data" EX 300` | O(1), mínima memoria, expiración automática |
| Objeto con varios campos que se actualizan por separado | Hash | `HSET user:1000 name "Juan"` | Actualización parcial sin leer todo; ~30% menos memoria que JSON |
| Cola FIFO (primero en entrar, primero en salir) | List | `LPUSH` + `BRPOP` | Inserción/eliminación O(1) por extremos |
| Pila LIFO (último en entrar, primero en salir) | List | `LPUSH` + `LPOP` | Misma estructura, uso distinto |
| Conjunto sin duplicados | Set | `SADD likes:post:1 "user:1000"` | O(1) membresía, operaciones de conjuntos |
| Ranking / leaderboard / timeline | Sorted Set | `ZADD leaderboard 1500 "player:1"` | Ordenado por score, O(log N) |
| Contador atómico (vistas, likes) | String numérico | `INCR views:product:456` | O(1), atómico bajo concurrencia |
| Geolocalización | Geo | `GEOADD locations 2.35 48.85 "Paris"` | Búsqueda por radio y distancia |
| Manipulación de bits (flags, features) | Bitmap | `SETBIT user:1000:features 0 1` | Muy eficiente en memoria para banderas |

**Regla práctica:** si solo hay que guardar un valor con TTL → `String`. Si hay campos independientes → `Hash`. Si hay que ordenar por puntuación → `Sorted Set`. En caso de duda, empieza por `String` y migra si necesitas más funcionalidad.

> **Por qué importa esto y no solo "qué comando uso":** la pregunta de examen no es "¿qué comando inserta un elemento?", sino "dado este patrón de acceso, ¿qué estructura minimiza latencia y memoria?". El criterio siempre es: **¿cómo se va a leer/escribir el dato en producción?**

## 3. Embeber vs referenciar datos

Es la decisión de modelado más importante del tema: **¿guardo todos los campos de un objeto en un único Hash (embeber) o los reparto en claves `SET` independientes (referenciar)?**

### Opción A — Embeber (Hash)

```redis
HSET user:1000:profile
    nombre "Juan García"
    email "juan@email.com"
    ciudad "Madrid"
    telefono "+34 600 123 456"
    fecha_registro "2025-01-15"

HGET user:1000:profile nombre     # "Juan García"
HGETALL user:1000:profile         # todos los campos
```

### Opción B — Referenciar (claves separadas)

```redis
SET user:1000:nombre "Juan García"
SET user:1000:email "juan@email.com"
SET user:1000:ciudad "Madrid"
SET user:1000:telefono "+34 600 123 456"
SET user:1000:fecha_registro "2025-01-15"

GET user:1000:nombre              # "Juan García"
# Para leer todo: múltiples GET (menos eficiente)
```

### Comparativa

| Criterio | Embeber (Hash) | Referenciar (claves separadas) |
|---|---|---|
| Memoria | ~30% menos (un solo prefijo de clave) | Más (prefijo repetido por campo) |
| Acceso parcial | Sí — `HGET` lee solo un campo | Sí — `GET` lee solo una clave |
| Acceso completo | Óptimo — `HGETALL` en una llamada | Costoso — múltiples `GET` (roundtrips) |
| TTL por campo | No — el TTL es de toda la clave | Sí — cada clave tiene su propio TTL |
| Actualización parcial | `HSET` cambia solo un campo | `SET` cambia solo una clave |
| Atomicidad | `HSET`/`HGET` no son atómicos entre campos | Necesita `MULTI`/`EXEC` para atomicidad conjunta |
| Escalabilidad en clúster | Todo el Hash vive en un solo nodo | Las claves pueden repartirse entre nodos |

**Reglas prácticas para decidir:**
1. Si el objeto tiene varios campos que **siempre se leen juntos** (p. ej. el perfil de un usuario) → **embebe (Hash)**.
2. Si algún campo necesita un **TTL distinto** al resto, o **escala de forma independiente** (p. ej. sesión con TTL de 30 min vs perfil que no expira) → **referencia (claves separadas)**.
3. Si necesitas **atomicidad entre varios campos** → usa `MULTI`/`EXEC` o *scripts* Lua, sea cual sea la opción elegida.

> **Caso real — Instagram:** embebe los datos de perfil en Hashes (nombre, bio, avatar) porque se leen siempre juntos. Pero usa claves separadas para contadores (followers, posts) porque tienen TTLs y patrones de escalado distintos entre sí.

**Idea clave para el examen:** el proceso de decisión es una secuencia de preguntas:
`¿Se leen siempre juntos?` → Hash · `¿Tienen TTLs diferentes?` → claves separadas · `¿Necesito atomicidad?` → `MULTI`/`EXEC` o Lua.

## 4. Modelado de feeds y timelines (caso de estudio)

Uno de los usos más frecuentes de Redis en redes sociales es modelar **feeds** (muro de noticias) y **timelines** (cronología de publicaciones de un usuario).

### Twitter — Timeline como Sorted Set

```redis
# 1. Al publicar un tweet, se añade a la timeline del autor
ZADD user:1000:timeline 1726500000 "tweet:abc123"

# 2. Fan-out en escritura: se copia a los timelines de cada seguidor
ZADD user:2000:timeline 1726500000 "tweet:abc123"
ZADD user:3000:timeline 1726500000 "tweet:abc123"
ZADD user:4000:timeline 1726500000 "tweet:abc123"

# 3. Leer los 50 tweets más recientes (score = timestamp)
ZREVRANGE user:1000:timeline 0 49 WITHSCORES
# → ["tweet:xyz789", "tweet:abc123", ...]

# 4. Tweets de los últimos 30 minutos
ZREVRANGEBYSCORE user:1000:timeline $(date +%s) $(($(date +%s) - 1800))
```

Twitter usa el **timestamp del tweet como `score`**, así el orden cronológico viene gratis (`ZREVRANGE` = más recientes primero). Un usuario con millones de seguidores hace que el *fan-out* en escritura sea costoso — por eso Redis actúa como caché de escritura rápida, con una base de datos persistente como respaldo.

### Instagram — Feed híbrido (Sorted Set + Hash + Set)

```redis
# 1. Sorted Set para el orden cronológico del feed
ZADD user:5000:feed 1726500000 "post:post123"

# 2. Hash con los datos del post (embebido, se leen juntos)
HSET post:post123
    autor "ana_foto"
    likes 1247
    comentarios 89
    media_url "https://cdn.instagram.com/post123.jpg"
    fecha "2025-09-16T10:00:00Z"

# 3. Set para saber quién ya vio el post (evita duplicados)
SADD post:post123:vistos 5000 5001 5002

# 4. Contador de likes atómico
INCR likes:post:post123
```

> **Dato real:** Instagram genera ~100 millones de "me gusta" al día, cada uno resuelto con un `INCR` atómico. Los feeds usan Sorted Sets con TTL de 24 h, de forma que los posts antiguos se eliminan solos de la caché.

### Fan-out en escritura vs en lectura

| Patrón | Cómo funciona | Ventajas | Inconvenientes |
|---|---|---|---|
| **Escritura (push)** | Al publicar, se copia el post a todos los timelines de los seguidores | Lectura rápida O(1) | Escritura cara (N copias por N seguidores) |
| **Lectura (pull)** | Al leer, se buscan los posts de las cuentas seguidas | Escritura barata (1 solo post) | Lectura lenta (hay que consultar N cuentas) |
| **Híbrido** | Push para la mayoría + *pull*/caché con TTL para cuentas muy seguidas | Equilibrio entre ambos | Mayor complejidad de implementación |

Instagram combina ambos: **fan-out en escritura** para usuarios normales (< 100 000 seguidores) y **fan-out en lectura** para celebridades (> 100 000 seguidores), evitando así replicar un post a millones de timelines de golpe.

**Por qué importa:** este es el ejemplo canónico de que la estructura de datos correcta (Sorted Set) no basta por sí sola — también hay que decidir *cuándo* se escribe el dato (al publicar o al leer), y esa decisión depende de la escala del usuario que publica.

## 5. Strings — el tipo básico

Los **Strings** son el tipo más simple y versátil: pueden contener texto, números, bytes o datos serializados (JSON, XML...). Es la estructura por defecto cuando el objeto **tiene un único valor**.

### Representación interna (contenido ampliable, no imprescindible para usar Redis)

| Codificación | Cuándo se usa | Característica |
|---|---|---|
| `int` | El string es un entero (hasta 2³²−1) | Ocupa muy poca memoria |
| `embstr` | Strings pequeños (< 44 bytes) | Se almacena junto al descriptor, en un solo bloque |
| `raw` | Strings grandes (> 44 bytes) | Se almacena en un bloque de memoria separado |

### Operaciones

```redis
# Almacenamiento básico
SET user:1000:name "Juan García"
GET user:1000:name                  # "Juan García"

# Strings numéricos (contadores atómicos)
SET product:456:views 0
INCR product:456:views              # 1
INCR product:456:views              # 2
INCRBY product:456:views 10         # 12
DECR product:456:views              # 11
DECRBY product:456:views 5          # 6

# Strings con expiración
SETEX session:abc123 1800 "userId:1000"   # TTL 30 min
SET cache:product:456 "iPhone" EX 300     # TTL 5 min
SET lock:resource1 "owner-123" NX EX 10   # lock con TTL 10s (solo si no existe)

# Operaciones avanzadas
APPEND user:1000:name " García"     # añadir al final
STRLEN user:1000:name               # longitud: 14
SETRANGE user:1000:name 0 "Pedro"   # sobreescribir desde posición 0
GETRANGE user:1000:name 0 4         # substring: "Pedro"

# Lectura/escritura múltiple (más eficiente que N GET/SET)
MSET user:1000:name "Juan" user:1000:email "juan@email.com"
MGET user:1000:name user:1000:email
```

**¿Cuándo strings vs hashes?** Si el objeto tiene **un solo campo** → string. Si tiene **varios campos que se actualizan por separado** → hash.

> **Caso real — GitHub:** usa `INCR` para *rate limiting* por usuario (5 000 peticiones/hora autenticadas). Cada usuario tiene una clave `ratelimit:{user_id}:{timestamp_hour}` que se incrementa en cada petición y expira automáticamente tras una hora — sin necesidad de un *cron* que limpie contadores viejos.

**Resumen:** tipo básico y versátil. Internamente se codifica como `int`, `embstr` (< 44 bytes) o `raw`. `INCR` para contadores atómicos, `SET ... EX` para TTL, `MSET`/`MGET` para operaciones múltiples más eficientes que llamadas individuales.

## 6. Hashes — campos y valores

Los **Hashes** almacenan pares **campo-valor** dentro de una única clave. Son ideales para representar objetos con varias propiedades (perfiles de usuario, productos, configuraciones) que necesitan **actualización parcial** sin reescribir todo el objeto.

### Representación interna

- **listpack** (antes *ziplist*): cuando el hash tiene pocos campos (< 128) y cada campo es pequeño (< 64 bytes). Estructura compacta, todo en un bloque contiguo de memoria — sin punteros por elemento, mínimo overhead. Su coste es que la inserción media es O(N) porque hay que desplazar elementos.
- **hash table**: cuando el hash crece más allá de esos umbrales. Usa una tabla hash clásica con *rehashing* incremental, con acceso O(1) por campo pero más overhead de memoria (punteros).

### Operaciones

```redis
# Crear hash con múltiples campos
HSET user:1000 name "Juan García"
HSET user:1000 email "juan@email.com"
HSET user:1000 age 28
HSET user:1000 city "Madrid"

# Crear hash de una vez (más eficiente: una sola llamada)
HSET user:1001 name "Ana López" email "ana@email.com" age 25

# Leer campos
HGET user:1000 name           # "Juan García"
HMGET user:1000 name email    # ["Juan García", "juan@email.com"]
HGETALL user:1000             # todos los campos y valores
HKEYS user:1000               # solo los nombres de campo
HVALS user:1000               # solo los valores

# Operaciones sobre campos
HEXISTS user:1000 email       # 1 (existe)
HLEN user:1000                # 4 (número de campos)
HDEL user:1000 city           # elimina el campo

# Incrementar campo numérico
HINCRBY user:1000 age 1              # 29
HINCRBYFLOAT user:1000 salary 500.50

# Búsqueda de campos sin bloquear el servidor (cursor)
HSCAN user:1000 0 MATCH na* COUNT 10  # campos que empiezan por "na"
```

### Hash vs string serializado (JSON)

| Aspecto | Hash | String serializado (JSON) |
|---|---|---|
| Actualización parcial | Sí (`HSET` de un solo campo) | No (leer → deserializar → modificar → serializar → escribir) |
| Memoria | Más eficiente (small hash encoding) | Mayor overhead (metadatos JSON) |
| Lectura completa | Una operación (`HGETALL`) | Una operación (`GET`) |
| Lectura parcial | Óptima (`HGET`) | Ineficiente (hay que leer todo y descartar) |
| Legibilidad | Campos individuales | JSON completo |
| Uso de memoria | ~30% menos que JSON | Más overhead |

> **Caso real — Instagram:** almacena datos de perfil en hashes (`user:123:profile` → `{name, bio, avatar_url}`), permitiendo actualizaciones parciales sin leer el documento completo. Cuando un usuario cambia solo su bio, se ejecuta `HSET user:123:profile bio "Nueva bio"` en lugar de leer todo el perfil, modificarlo y reescribirlo entero.

**Resumen:** mapea campo-valor dentro de una clave. `HSET`/`HGET` para acceso parcial. Internamente: listpack (pocos campos) → hash table (muchos campos). ~30% menos memoria que JSON serializado.

## 7. Lists — listas enlazadas

Las **Lists** son listas enlazadas bidireccionales que permiten inserción y eliminación eficiente **por ambos extremos**. Son ideales para colas (FIFO), pilas (LIFO) e historiales.

### Representación interna

- **listpack:** cuando la lista es pequeña — un solo bloque de memoria compacto.
- **quicklist:** cuando la lista crece — una lista doblemente enlazada de listpacks. Es la estructura por defecto desde Redis 3.2+, combinando la eficiencia de memoria del listpack con el acceso rápido de una lista enlazada, de forma transparente para el usuario.

### Operaciones

```redis
# Insertar por los extremos
LPUSH colas:tareas "tarea1"     # izquierda (inicio) — O(1)
RPUSH colas:tareas "tarea2"     # derecha (fin) — O(1)
LPUSHX colas:tareas "tarea0"    # solo si la lista ya existe

# Extraer por los extremos
LPOP colas:tareas               # izquierda → FIFO
RPOP colas:tareas               # derecha → LIFO
LPOP colas:tareas 3             # extraer 3 elementos de la izquierda

# Cola FIFO bloqueante (espera hasta que haya datos)
LPUSH colas:email "email1"
LPUSH colas:email "email2"
BRPOP colas:email 0             # bloquea indefinidamente
BRPOP colas:email 30            # bloquea máximo 30 segundos

# Rangos y acceso por índice
LRANGE colas:tareas 0 -1        # todos los elementos
LRANGE colas:tareas 0 9         # primeros 10 elementos
LINDEX colas:tareas 0           # elemento en posición 0
LINDEX colas:tareas -1          # último elemento

# Modificar elementos
LSET colas:tareas 0 "nueva_tarea"
LINSERT colas:tareas BEFORE "tarea1" "tarea0"

# Longitud y eliminación
LLEN colas:tareas               # longitud de la lista
LTRIM colas:tareas 0 99         # mantener solo los primeros 100 elementos
LREM colas:tareas 2 "tarea1"    # eliminar 2 ocurrencias de "tarea1"
```

**`BRPOP`/`BLPOP` = Blocking Pop.** El cliente entra en estado bloqueado *en la red*: no consume CPU ni memoria mientras espera. Redis lo despierta en cuanto hay datos en la lista, o al cumplirse el *timeout*. Es el patrón productor-consumidor clásico: el productor hace `LPUSH`, el consumidor hace `BRPOP` y espera de forma eficiente (mucho mejor que hacer *polling* cada 100 ms).

> **Analogía:** es como la caja de un supermercado. El cajero pone la siguiente compra en la cinta (`LPUSH`). El cliente espera hasta que haya una compra en la cinta (`BRPOP`). Si la cinta está vacía, el cajero no hace nada; en cuanto llega algo, empieza a trabajar.

> **Caso real — Twitter:** usa listas para colas de procesamiento de tweets y notificaciones push. Cada tweet pendiente de procesar se añade con `LPUSH` a una cola, y los *workers* lo procesan con `BRPOP`. Esto garantiza que cada notificación se procese exactamente una vez y permite tener múltiples *workers* trabajando en paralelo sobre la misma cola.

**Resumen:** listas enlazadas bidireccionales. `LPUSH`/`RPUSH` para insertar, `LPOP`/`RPOP` para extraer. `BRPOP`/`BLPOP` para colas bloqueantes (patrón productor-consumidor). Internamente: listpack → quicklist.

## 8. Sets — conjuntos únicos

Los **Sets** son conjuntos **desordenados** de strings únicos: no permiten duplicados y soportan operaciones de teoría de conjuntos (intersección, unión, diferencia).

### Representación interna

- **intset:** cuando todos los elementos son enteros y el conjunto es pequeño. Es un array contiguo de enteros **ordenados**, con búsqueda binaria O(log N). Para conjuntos pequeños de enteros (hasta ~128 elementos), es más eficiente que una hash table completa porque no usa punteros por elemento. Al crecer demasiado, se convierte en hash table.
- **listpack:** cuando el conjunto es pequeño y los elementos son strings cortos.
- **hash table:** cuando el conjunto crece más allá de esos umbrales — acceso O(1) por elemento, pero con más overhead de memoria.

### Operaciones

```redis
# Añadir miembros
SADD usuarios:online "user:1000"
SADD usuarios:online "user:1001"
SADD usuarios:online "user:1002"
SADD usuarios:online "user:1000"   # ignorado (duplicado)

# Verificar membresía
SISMEMBER usuarios:online "user:1000"          # 1 (true)
SISMEMBER usuarios:online "user:9999"          # 0 (false)
SMISMEMBER usuarios:online "user:1000" "user:9999"  # [1, 0]

# Obtener miembros
SMEMBERS usuarios:online       # todos los miembros
SRANDMEMBER usuarios:online 3  # 3 miembros aleatorios
SCARD usuarios:online          # número de miembros (3)

# Eliminar miembros
SREM usuarios:online "user:1000"

# Operaciones de conjuntos
SADD likes:post:1 "user:1000" "user:1001" "user:1002"
SADD likes:post:2 "user:1001" "user:1002" "user:1003"

SINTER likes:post:1 likes:post:2     # intersección: quién dio like a AMBOS posts
                                      # → user:1001, user:1002
SUNION likes:post:1 likes:post:2     # unión: quién dio like a CUALQUIER post
                                      # → user:1000, user:1001, user:1002, user:1003
SDIFF likes:post:1 likes:post:2      # diferencia: solo en post:1
                                      # → user:1000

SINTERSTORE comunes likes:post:1 likes:post:2   # guarda el resultado en una nueva clave
```

> **Caso real — GitHub:** usa sets para rastrear usuarios que han dado *star* a un repositorio. `SADD repo:456:stars "user:1000"` añade una estrella; `SCARD repo:456:stars` cuenta el total; `SINTER repo:456:stars repo:789:stars` encuentra usuarios que han dado estrella a ambos repositorios (por ejemplo, para recomendaciones).

**Resumen:** conjuntos sin duplicados. `SINTER` (intersección), `SUNION` (unión), `SDIFF` (diferencia). Internamente: intset (solo enteros) → listpack → hash table.

## 9. Sorted Sets — conjuntos ordenados

Los **Sorted Sets** (`ZSET`) son como los sets, pero con una **puntuación (`score`)** asociada a cada miembro. Los miembros se mantienen siempre ordenados por puntuación (de menor a mayor). Son ideales para **rankings, leaderboards y timelines**.

### Representación interna: Skip List

- **listpack:** cuando el sorted set es pequeño (< 128 miembros y scores < 64 bytes).
- **skip list + hash table:** cuando el sorted set crece. La *skip list* permite recorrer rangos ordenados en O(log N), y la hash table permite acceso directo O(1) por miembro (para `ZSCORE`, por ejemplo). Redis combina ambas estructuras internamente para cada sorted set grande.

**¿Cómo funciona una Skip List?** Imagina una lista enlazada ordenada. Ahora se le añaden "atajos": algunos elementos tienen punteros que saltan 2 posiciones, otros 4, etc., en varios niveles. Para buscar, se empieza por el nivel más alto (saltos largos) y, al pasarse del valor buscado, se baja un nivel y se hacen saltos más pequeños. El resultado es una búsqueda O(log N) con una implementación mucho más simple que un árbol balanceado (no requiere rebalanceo).

Ejemplo con la secuencia `1, 2, 3, 4, 5, 6`:
- Nivel 0 (lista completa): `1 → 2 → 3 → 4 → 5 → 6`
- Nivel 1 (atajos medios): `1 → 2 → 4 → 5 → 6`
- Nivel 2 (atajos largos): `1 → 4 → 6`

Para buscar el `6`, en vez de recorrer los 6 nodos uno a uno, se puede saltar `1 → 4 → 6` en el nivel más alto: 2 saltos en lugar de 5.

### Operaciones

```redis
# Añadir miembros con puntuación
ZADD leaderboard 1500 "player:1000"
ZADD leaderboard 2300 "player:1001"
ZADD leaderboard 1800 "player:1002"
ZADD leaderboard 2300 "player:1003"

# Añadir varios miembros de una vez
ZADD leaderboard 2100 "player:1004" 1900 "player:1005"

# Obtener rango (de menor a mayor)
ZRANGE leaderboard 0 -1 WITHSCORES        # todos, con puntuación
ZRANGE leaderboard 0 2 WITHSCORES         # los 3 con menor score
ZREVRANGE leaderboard 0 2 WITHSCORES      # top 3 (mayor a menor)

# Puntuación y rango de un miembro
ZSCORE leaderboard "player:1000"          # 1500
ZRANK leaderboard "player:1000"           # posición (0-based, de menor a mayor)
ZREVRANK leaderboard "player:1000"        # posición de mayor a menor

# Incrementar puntuación
ZINCRBY leaderboard 100 "player:1000"     # 1600
ZINCRBY leaderboard -50 "player:1001"     # 2250

# Rangos por puntuación
ZRANGEBYSCORE leaderboard 1000 2000            # entre 1000 y 2000
ZRANGEBYSCORE leaderboard 1000 2000 LIMIT 0 5  # primeros 5
ZREVRANGEBYSCORE leaderboard 2000 1000         # de mayor a menor

# Eliminar
ZREM leaderboard "player:1005"
ZREMRANGEBYSCORE leaderboard 0 1000       # elimina scores < 1000
ZREMRANGEBYRANK leaderboard 0 2           # elimina los 3 primeros

# Contar
ZCARD leaderboard                    # número total de miembros
ZCOUNT leaderboard 1000 2000         # miembros con score entre 1000 y 2000
```

> **Caso real — Twitter:** almacena timelines como Sorted Sets (`timeline:{user_id}` → `{timestamp: post_id}`), manteniendo los ~800 posts más recientes por usuario. Cada tweet de un usuario con 10 millones de seguidores se replica a 10 millones de Sorted Sets en menos de un segundo. El score es el timestamp, lo que permite obtener los posts más recientes con `ZREVRANGE`.

> **Conexión con T7:** en el tema de bases de datos distribuidas se verá que Netflix modela el historial de reproducción con tablas particionadas en Cassandra, **no** con Sorted Sets. Cada tecnología tiene su mejor caso de uso según la escala y el patrón de acceso — Redis sorted sets brillan en rankings *en memoria* de tamaño acotado; Cassandra brilla en históricos masivos y duraderos.

**Resumen:** conjuntos ordenados por `score`. Ideales para rankings (`ZADD`, `ZREVRANGE`). Internamente: listpack → skip list + hash table. O(log N) por operación.

## 10. Caso real completo: Twitter e Instagram (métricas)

### Twitter — Sorted Sets para timelines
Ver la sección 4 y el Tema 3.1 para las métricas detalladas de latencia y throughput.

### Instagram — feed híbrido y métricas

Instagram usa un **patrón híbrido** para generar el feed de noticias:

- **Usuarios normales (< 100 000 seguidores):** *fan-out on write*. Cada post se copia a los timelines de todos sus seguidores usando Redis Sorted Sets.
- **Celebridades (> 100 000 seguidores):** *fan-out on read*. El feed se genera al vuelo consultando Cassandra, sin replicar el post a Redis.

| Métrica | Valor |
|---|---|
| Usuarios activos diarios | 500 millones |
| Lecturas de feed/día | 2 500 millones |
| Almacenamiento en Redis | ~1,2 TB (40 nodos × 32 GB) |
| Uploads de fotos/vídeos/día | 100 millones |

**Lección:** no existe una solución única para feeds. Instagram combina *fan-out on write* (para usuarios con pocos seguidores) y *fan-out on read* (para celebridades) para equilibrar rendimiento y consumo de memoria. Esta es la idea que hay que saber justificar en un examen: **la estructura de datos correcta no compensa una mala estrategia de fan-out, y viceversa** — hay que decidir ambas cosas juntas según la escala de cada usuario.

## 11. Resumen visual de las 5 estructuras

| Estructura | Qué es | Comandos clave | Complejidad típica |
|---|---|---|---|
| **String** | Texto, números, bytes | `SET` / `GET` / `INCR` | O(1) — acceso directo |
| **Hash** | Mapa campo → valor | `HSET` / `HGET` / `HGETALL` | O(1) por campo |
| **List** | Lista enlazada | `LPUSH` / `RPUSH` / `LRANGE` | O(1) extremos, O(N) rango |
| **Set** | Conjunto sin duplicados | `SADD` / `SINTER` / `SDIFF` | O(1) inserción/membresía |
| **Sorted Set** | Conjunto con puntuación | `ZADD` / `ZRANGE` / `ZRANK` | O(log N) por operación |

## 12. Redis Modules — ampliando las capacidades

Desde Redis 5+, los módulos convierten Redis en una plataforma completa, más allá de la caché clave-valor:

- **RediSearch** — búsqueda full-text, *fuzzy*, por rango numérico y por tags. Crea índices sobre Hashes o JSON. Sustituye a Elasticsearch en casos simples.

```redis
# Crear índice sobre hashes con prefijo "product:"
FT.CREATE idx:products ON HASH PREFIX 1 product: SCHEMA
    name TEXT
    price NUMERIC
    category TAG

HSET product:1 name "iPhone 15" price 999 category "phones"
HSET product:2 name "Samsung Galaxy" price 899 category "phones"
HSET product:3 name "MacBook Pro" price 2499 category "laptops"

FT.SEARCH idx:products "iPhone"                  # búsqueda full-text
FT.SEARCH idx:products "@price:[800 1000]"       # rango de precio
FT.SEARCH idx:products "@category:{phones}"      # filtro por tag
```

- **RedisJSON** — almacena y consulta JSON de forma nativa, sin serializar/deserializar manualmente. Soporta rutas JSON y actualización parcial de un solo campo dentro del documento.

```redis
JSON.SET user:1000 $ '{"name":"Juan","address":{"city":"Madrid","zip":"28001"}}'

JSON.GET user:1000 $.name             # "Juan"
JSON.GET user:1000 $.address.city     # "Madrid"

JSON.SET user:1000 $.address.city "Barcelona"   # actualización parcial
```

- **RedisTimeSeries** — datos de series temporales con retención automática y agregaciones (`avg`, `sum`, `min`, `max`). Ideal para métricas, IoT y monitoreo.

- **RedisBloom** — filtros probabilísticos:
  - **HyperLogLog:** cuenta elementos únicos con ~0,81% de error usando solo 12 KB de memoria. Ideal para contar visitantes únicos.
  - **Bloom Filter:** verifica pertenencia a un conjunto sin almacenar cada elemento. Útil para evitar consultas a la BD por datos que seguro no existen.
  - **Cuckoo Filter:** alternativa al Bloom Filter con soporte para eliminación de elementos.

> **Caso real — Instagram:** usa HyperLogLog para contar usuarios únicos que ven una Story sin almacenar cada usuario individualmente. Con solo 12 KB de memoria por Story, consiguen una precisión del 99,2% para *counts* de hasta 4 000 millones de elementos únicos — una alternativa a un `SADD` por visor, que sería inviable en memoria a esa escala.

**Resumen módulos:** RediSearch (búsqueda full-text), RedisJSON (JSON nativo), RedisTimeSeries (series temporales), RedisBloom (HyperLogLog, Bloom Filter). Amplían Redis más allá del clave-valor puro.

## 13. Cuándo aplicar todo esto en la práctica

- Elige la estructura de datos **antes** de escribir datos: cambiarla después es costoso y requiere migración.
- Usa Hashes para objetos con múltiples campos (ahorra ~30% de memoria frente a strings serializados en JSON).
- Para IDs únicos autoincrementales, `INCR` es más simple y eficiente que generar UUIDs.
- Los Sorted Sets son ideales para rankings y feeds temporales: usar el `score` como timestamp resuelve el orden cronológico de forma gratuita.
- Usa `MEMORY USAGE <key>` para medir cuánta memoria consume una clave concreta y así poder comparar y optimizar el modelado elegido.

## 14. Preguntas de autoevaluación

**1. ¿Qué estructura usarías para guardar el perfil de un usuario con nombre, email y ciudad, que siempre se leen juntos?**
> Un **Hash** (`HSET user:1000 name ... email ... ciudad ...`), porque los campos se leen siempre juntos y así se ahorra memoria y se permite `HGETALL` en una sola llamada.

**2. Si ese mismo usuario tiene un campo con TTL de 30 minutos (sesión) y otro sin expiración (perfil), ¿qué harías?**
> Separar en dos claves distintas (referenciar): una para la sesión con `SETEX`/`EX` de 30 min, y otra (Hash) para el perfil sin TTL. Un Hash único no permite TTL por campo, solo por clave completa.

**3. ¿Por qué Twitter usa Sorted Sets en lugar de Lists para las timelines?**
> Porque necesita mantener el orden cronológico y poder consultar por rango de tiempo (`ZREVRANGEBYSCORE`) usando el timestamp como `score`. Una List no tiene noción de puntuación ni permite búsquedas eficientes por rango de valores, solo por posición.

**4. Si un post de Instagram recibe 10 millones de "me gusta", ¿qué estructura usarías para el contador y por qué?**
> Un **String numérico con `INCR`**: operación atómica O(1), sin necesidad de leer el valor antes de incrementarlo, evitando condiciones de carrera bajo alta concurrencia. Usar un Set con un miembro por usuario sería mucho más costoso en memoria y no es necesario si solo se quiere el conteo (aunque si se necesita saber *quién* dio like, se combinaría con un Set o HyperLogLog).

**5. ¿Cuál es la diferencia entre `SINTER` y `SUNION`?**
> `SINTER` devuelve los elementos presentes en **todos** los conjuntos (intersección); `SUNION` devuelve los elementos presentes en **al menos uno** de los conjuntos (unión).

**6. ¿Qué ventaja tiene `BRPOP` frente a hacer `RPOP` en un bucle (`polling`)?**
> `BRPOP` bloquea la conexión del cliente a nivel de red sin consumir CPU, y Redis despierta al cliente en cuanto hay datos disponibles (o al cumplirse el timeout). El *polling* con `RPOP` desperdicia CPU y añade latencia media (hasta el intervalo del sondeo).

**7. ¿Qué es un `intset` y cuándo lo usa Redis?**
> Es la codificación interna de un Set cuando **todos** sus elementos son enteros y el conjunto es pequeño (hasta ~128 elementos). Es un array ordenado de enteros con búsqueda binaria O(log N), más eficiente en memoria que una hash table porque no usa punteros por elemento.

**8. ¿Qué estructura interna usa un Sorted Set grande y qué complejidad ofrece?**
> Una combinación de **skip list** (para recorridos ordenados y por rango, O(log N)) y **hash table** (para acceso directo O(1) por miembro, como en `ZSCORE`).

**9. Explica la diferencia entre fan-out en escritura y fan-out en lectura para un feed social.**
> Fan-out en escritura: al publicar, se copia el contenido a los timelines de todos los seguidores (lectura rápida, escritura cara). Fan-out en lectura: al leer, se consultan las publicaciones de las cuentas seguidas en el momento (escritura barata, lectura más lenta). Instagram usa un híbrido según el número de seguidores del autor.

**10. ¿Por qué `HSET` puede ser más eficiente en memoria que guardar el mismo objeto como JSON serializado en un String?**
> Porque un Hash usa una codificación compacta (listpack) sin el overhead de sintaxis JSON (comillas, llaves, nombres de campo repetidos en texto plano) y permite lectura/escritura de campos individuales sin deserializar el objeto completo. En la práctica supone un ahorro aproximado del 30% de memoria.

**11. ¿Qué comando usarías para saber cuántos usuarios están online a la vez, sin duplicados?**
> `SADD usuarios:online <user_id>` para cada conexión, y `SCARD usuarios:online` para obtener el total sin duplicados (O(1)).

**12. ¿Cuándo usarías HyperLogLog en lugar de un Set para contar elementos únicos?**
> Cuando la cardinalidad puede ser muy alta (millones/miles de millones) y no es necesario saber *cuáles* son los elementos, solo *cuántos* únicos hay, y se puede tolerar un pequeño margen de error (~0,81%). Un Set almacenaría cada elemento (mucha memoria); HyperLogLog usa solo ~12 KB independientemente del número de elementos.

**13. ¿Qué problema resuelve `MULTI`/`EXEC` que `HSET` y `HGET` por sí solos no resuelven?**
> La atomicidad entre varias operaciones sobre distintos campos o claves. `HSET`/`HGET` son atómicos *individualmente*, pero si se necesita que varias operaciones se ejecuten como una unidad indivisible (sin que otro cliente intervenga entre medias), hace falta `MULTI`/`EXEC` (o un script Lua).

**14. Da un ejemplo de cuándo usarías RedisJSON en lugar de un Hash.**
> Cuando el objeto tiene una estructura **anidada** (por ejemplo, `address` con subcampos `city` y `zip` dentro de un usuario) y se necesita consultar o actualizar rutas anidadas directamente (`$.address.city`), algo que un Hash plano (campo-valor de un solo nivel) no soporta de forma nativa.

**15. Si tuvieras que justificar en un examen por qué elegiste Sorted Set y no List para un ranking de videojuego, ¿qué dirías?**
> Un ranking necesita mantener a los jugadores **ordenados por puntuación** y poder consultar la posición (`ZRANK`) o el top N (`ZREVRANGE`) de forma eficiente (O(log N)). Una List solo mantiene orden de inserción y no tiene noción de puntuación, por lo que habría que reordenarla manualmente en cada actualización, algo muy costoso (O(N log N) cada vez).
