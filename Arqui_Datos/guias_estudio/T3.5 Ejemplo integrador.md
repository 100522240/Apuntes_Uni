## 1. Resumen general y objetivos

Este tema cierra el bloque de Redis con un **caso práctico completo**: una tienda en línea que integra todos los conceptos aprendidos — Strings, Hashes, Sorted Sets, TTL, caché, sesiones, contadores, rate limiting y rankings — en un único sistema cohesionado. El objetivo no es aprender conceptos nuevos, sino ver cómo se **combinan** en la práctica y razonar sobre las decisiones de diseño.

**Resultados de aprendizaje:**
- Integrar todos los conceptos de Redis en un caso práctico completo.
- Aplicar patrones de caché, sesiones, contadores y rankings en una tienda en línea.
- Comprender cómo se combinan las diferentes estructuras de datos de Redis en un sistema real.

La idea central: **ningún concepto de Redis funciona solo**. Un sistema real combina estructuras de datos distintas (Hashes para catálogo y carrito, Sorted Sets para rankings y rate limiting, Strings para sesiones y contadores) con estrategias distintas (Cache-Aside para el catálogo, TTL para sesiones, INCR atómico para métricas). El reto no está en saber usar cada pieza por separado, sino en saber cuál usar y cuándo.

## 2. Contexto: Tienda en línea

La tienda en línea es el hilo conductor que conecta todos los conceptos del Tema 3. La arquitectura es simple: una **Aplicación Backend** (C#/.NET, Node.js, Python) habla con **Redis** para datos calientes y con **MariaDB** para persistencia.

### Necesidades del sistema y cómo Redis las resuelve

| Necesidad | Concepto Redis | Ejemplo de clave | TTL |
|---|---|---|---|
| Catálogo de productos | Hashes + caché (Cache-Aside) | `product:123:info → {name, price, stock}` | 5 min |
| Sesiones de usuario | Claves con TTL | `session:abc123 → userId` | 30 min |
| Contadores de métricas | INCR atómico | `views:product:123` | Sin TTL |
| Rate limiting | Sorted Sets | `ratelimit:user:1000` | 1 hora |
| Top productos | Sorted Sets | `top:sales → {product: score}` | Sin TTL |
| Carrito de compra | Hashes | `cart:userId → {product: qty}` | 24 horas |

### Por qué cada elección

- **Hashes para catálogo y carrito:** permiten leer/escribir campos individuales (`HGET`, `HSET`, `HINCRBY`) sin serializar/deserializar el objeto completo. Si el carrito tiene 10 productos, `HINCRBY cart:user:1000 "product:456" 1` modifica solo ese producto de forma atómica.
- **TTL para sesiones:** la sesión expira automáticamente si el usuario no actúa. `SETEX` garantiza que el SET y el TTL se aplican atómicamente — nunca puede quedar una sesión sin TTL por un fallo de la aplicación entre `SET` y `EXPIRE`.
- **INCR para vistas y compras:** operación atómica — nunca hay condiciones de carrera aunque lleguen mil peticiones simultáneas.
- **Sorted Sets para rate limiting y rankings:** `ZADD` + `ZCARD` para rate limiting con ventana deslizante; `ZINCRBY` + `ZREVRANGE` para rankings en tiempo real. Ambos usan scores numéricos ordenados como mecanismo central.
- **Sin TTL para contadores y rankings:** los contadores de vistas y el ranking de ventas son acumulativos — no tiene sentido que expiren. Se gestionan manualmente (reset diario, etc.) si fuera necesario.

## 3. Implementación completa

### 3.1 Redis CLI — Tienda en línea completa

```bash
# === CATÁLOGO DE PRODUCTOS (Cache-Aside) ===
SET product:456:info '{"name":"iPhone 15","price":999,"stock":50}' EX 300
GET product:456:info

# === SESIONES DE USUARIO ===
SET session:x7k2m9:userId "1000" EX 1800
SET session:x7k2m9:role "customer" EX 1800

# === CONTADORES DE MÉTRICAS ===
INCR views:product:456
INCRBY views:product:456 3        # Añadir 3 de golpe (ej. batch)
INCR purchases:product:456

# === RANKING DE PRODUCTOS ===
ZADD top:sales 150 "product:456"
ZADD top:sales 230 "product:789"
ZREVRANGE top:sales 0 9 WITHSCORES  # Top 10 (descendente)

# === CARRITO DE COMPRA ===
HSET cart:user:1000 "product:456" 2
HSET cart:user:1000 "product:789" 1
HGETALL cart:user:1000
HINCRBY cart:user:1000 "product:456" 1  # Añadir 1 más (atómico)

# === RATE LIMITING ===
ZADD ratelimit:user:1000 1726400000 "req-001"
ZREMRANGEBYSCORE ratelimit:user:1000 0 1726396400  # Eliminar peticiones fuera de ventana
ZCARD ratelimit:user:1000                           # Contar peticiones en la ventana
```

### 3.2 Implementación en C# (.NET)

```csharp
// C# — Conexión con Redis (StackExchange.Redis)
using StackExchange.Redis;
using MySqlConnector;

// Conexión a Redis
ConnectionMultiplexer redis = await ConnectionMultiplexer.ConnectAsync("localhost:6379");
IDatabase db = redis.GetDatabase();

// Cache-Aside: buscar producto
string cacheKey = "product:456:info";
string? cached = await db.StringGetAsync(cacheKey);

if (cached.IsNullOrEmpty)
{
    // Cache miss → consultar MariaDB con ADO.NET
    using var conn = new MySqlConnection("Server=localhost;Database=shop;Uid=root;Pwd=...");
    await conn.OpenAsync();
    using var cmd = new MySqlCommand("SELECT * FROM products WHERE id=456", conn);
    var result = await cmd.ExecuteReaderAsync();
    if (await result.ReadAsync())
    {
        var product = System.Text.Json.JsonSerializer.Serialize(new {
            name = result.GetString("name"),
            price = result.GetDecimal("price"),
            stock = result.GetInt32("stock")
        });
        await db.StringSetAsync(cacheKey, product, TimeSpan.FromMinutes(5));
        cached = product;
    }
}
// cached contiene el dato (de Redis o de MariaDB)
```

Este ejemplo integra todos los conceptos del bloque: estructuras de datos, caché, TTL, rate limiting, rankings y sesiones. Es la base para las prácticas PR4 y PR5.

## 4. Flujo completo de una compra

El flujo de una compra integra múltiples conceptos de Redis en una secuencia coherente:

```
Usuario → "Añadir al carrito"
  Backend → HSET cart:user:1000 "prod:456" 2 → Redis: OK

Usuario → "Ver catálogo"
  Backend → GET product:456:info → Redis
    [Cache hit]  → Redis devuelve {name: iPhone, price: 999}
    [Cache miss] → Redis devuelve null
                   → Backend: SELECT * FROM products WHERE id=456 → MariaDB
                   → Backend: SET product:456:info ... EX 300 → Redis
  Backend → Mostrar producto

Usuario → "Comprar"
  Backend → INCR purchases:product:456       (contador atómico de compras)
  Backend → ZINCRBY top:sales 1 "product:456" (actualizar ranking en tiempo real)
  Backend → INSERT INTO orders ...            (persistir en MariaDB — fuente de verdad)
  Backend → DEL cart:user:1000               (vaciar carrito)
  → "Completado"
```

**¿Por qué este flujo es un buen ejemplo de integración?**
- El **carrito** (Hash, TTL 24h) persiste entre peticiones sin tocar la BD.
- La **caché de productos** (Cache-Aside, TTL 5 min) evita hits repetidos a MariaDB.
- El **contador de compras** (INCR atómico) actualiza las métricas sin bloqueos ni condiciones de carrera.
- El **ranking** (ZINCRBY en Sorted Set) se actualiza en tiempo real con cada compra — no hace falta un batch nocturno.
- La **persistencia de la orden** va a MariaDB — Redis no es la fuente de verdad para datos transaccionales.
- El **vaciado del carrito** es una invalidación por evento (`DEL`), no por TTL — porque el estado cambia por la compra, no por el paso del tiempo.

## 6. Cuándo aplicar todo esto en la práctica

- **Diseña las claves ANTES del código** — documenta el patrón de nombrado (`entidad:id:campo`) para que todo el equipo sea consistente. Cambiar el esquema de claves en producción es doloroso.
- **Usa `MEMORY USAGE clave`** en Redis para ver el tamaño real de una clave y optimizar el modelado (p. ej. decidir si usar Hash vs String para el catálogo).
- **Para rate limiting**, elige entre contadores (`INCR`) o Sorted Sets según la ventana de tiempo: `INCR` + `EXPIRE` para ventanas fijas por minuto; Sorted Sets (`ZADD`/`ZREMRANGEBYSCORE`/`ZCARD`) para ventanas deslizantes más precisas.
- **En sesiones de usuario**, `SETEX clave TTL valor` es un punto de partida seguro y atómico — nunca separes `SET` de `EXPIRE`.
- **Testea con `redis-benchmark`** antes de desplegar para validar que el rendimiento es el esperado bajo carga.

## 7. Preguntas de autoevaluación

**1. ¿Por qué se usa un Hash y no un String para el carrito de compra?**
> Porque el carrito tiene múltiples campos (producto → cantidad) y el Hash permite operar sobre campos individuales de forma atómica (`HINCRBY cart:user:1000 "product:456" 1` para añadir una unidad) sin serializar/deserializar el objeto completo. Con un String habría que hacer GET → deserializar → modificar → serializar → SET, lo que introduce riesgo de condición de carrera si dos peticiones modifican el carrito simultáneamente.

**2. El catálogo de productos usa Cache-Aside con TTL de 5 minutos. ¿Por qué no Write-Through?**
> Porque el catálogo se lee con mucha más frecuencia de lo que se escribe. Cache-Aside es ideal para datos con alta ratio lectura/escritura: solo se carga en caché lo que realmente se consulta. Write-Through doblaría el coste de cada actualización de producto (escribir en Redis Y en MariaDB de forma síncrona), lo cual no aporta beneficio cuando las actualizaciones son infrecuentes y la consistencia eventual (TTL de 5 min) es aceptable.

**3. ¿Por qué se usa `INCR` para los contadores de vistas y compras, en lugar de leer, incrementar y escribir?**
> Porque `INCR` es una operación atómica: Redis lo ejecuta como una sola instrucción, sin posibilidad de condición de carrera. Si dos peticiones simultáneas hicieran GET → +1 → SET por separado, podrían leer el mismo valor y la segunda escritura sobreescribiría el incremento de la primera (pérdida de 1 vista). Con `INCR` es imposible: cada llamada incrementa el contador exactamente en 1, sin importar la concurrencia.

**4. ¿Por qué se vacía el carrito con `DEL cart:user:1000` después de completar la compra, en lugar de esperar al TTL de 24 horas?**
> Por coherencia del estado: una vez procesada la compra, el carrito no debe seguir accesible. Esperar al TTL significaría que el usuario podría "ver" un carrito con productos que ya compró durante hasta 24 horas — una experiencia incorrecta. La invalidación explícita con `DEL` es la práctica correcta para datos que cambian de estado por un evento (compra completada), no por el paso del tiempo. El TTL de 24h solo sirve como red de seguridad (carrito abandonado).

**5. En el flujo de compra, ¿por qué se usa `ZINCRBY top:sales 1 "product:456"` y no `ZADD top:sales <nuevo_score> "product:456"`?**
> Porque `ZINCRBY` incrementa el score del elemento en el Sorted Set de forma atómica, sin necesidad de conocer el valor actual. Con `ZADD` habría que hacer `ZSCORE` → leer el score → sumar 1 → `ZADD` con el nuevo valor, introduciendo una condición de carrera si dos compras del mismo producto ocurren simultáneamente. `ZINCRBY` es la operación atómica equivalente a `INCR` pero para Sorted Sets.

**6. ¿Qué es lo que Redis NO debería ser en la arquitectura de la tienda en línea?**
> La fuente de verdad para datos transaccionales críticos (órdenes, pagos, inventario exacto). Redis es la capa "hot data" para velocidad: caché de catálogo, sesiones, contadores aproximados y rankings. Las órdenes van a MariaDB porque necesitan garantías ACID (atomicidad, consistencia, aislamiento, durabilidad) que Redis no ofrece por diseño. Redis complementa la BD, no la sustituye.

**7. Si la tienda en línea crece de 1.000 a 1.000.000 de usuarios diarios, ¿qué cambios de arquitectura de datos necesitarías en Redis?**
> Con 1M de usuarios/día, un único nodo Redis podría saturarse. Los cambios: (1) **Replicación** con 1 primary + 2-3 réplicas para escalar lecturas (catálogo, sesiones); (2) **Sentinel** para failover automático del primary; (3) Evaluar **Redis Cluster** si el dataset supera la RAM de un único nodo o la tasa de escritura supera la capacidad del primary; (4) Revisar la política de evicción (`allkeys-lru`) y `maxmemory` para gestionar la mayor presión de memoria.

**8. ¿Qué patrón de caché usarías para los 10.000 productos con 500.000 usuarios diarios? Justifica.**
> **Cache-Aside** con TTL de 5-15 minutos y jitter (±10%). Razones: (1) los productos se leen mucho más de lo que se actualizan — Cache-Aside es óptimo para alta ratio lectura/escritura; (2) es la estrategia más simple de implementar y depurar; (3) con 10.000 productos, el dataset de caché es manejable en RAM (pocos MB si cada producto es ~1KB); (4) los productos más vendidos concentran la mayor parte del tráfico (regla de Pareto), por lo que el hit rate natural será alto. El jitter en el TTL evita el *thundering herd* si muchos productos populares expiran a la vez.

**9. ¿Por qué se usa `ZREVRANGE top:sales 0 9 WITHSCORES` y no `ZRANGE` para obtener el top 10?**
> Porque `ZREVRANGE` devuelve los elementos ordenados de mayor a menor score (descendente), que es lo que necesita un ranking de ventas: el producto más vendido primero. `ZRANGE` devuelve de menor a mayor (ascendente), por lo que mostraría el producto menos vendido primero — lo opuesto de un "top 10". Con `0 9` se piden los primeros 10 elementos del orden descendente.

**10. ¿Cuál es la diferencia entre invalidación por TTL y por evento, y cuándo usar cada una en la tienda?**
> La invalidación por **TTL** borra la clave automáticamente al expirar (p. ej., el catálogo de productos a los 5 min). Es adecuada cuando el dato cambia con poca frecuencia y una consistencia eventual es aceptable. La invalidación por **evento** (`DEL clave`) borra la clave explícitamente cuando algo ocurre (p. ej., vaciar el carrito tras la compra). Es adecuada cuando el dato cambia de estado por una acción concreta y no se puede tolerar que el dato obsoleto persista hasta el TTL. En la tienda: TTL para caché de catálogo, evento para el carrito y la sesión en logout.
