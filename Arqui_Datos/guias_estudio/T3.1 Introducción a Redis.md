## 1. ¿Qué es Redis?

**Redis** es un almacén de datos en memoria, de código abierto, creado por **Salvatore Sanfilippo** en 2009 para resolver un problema real de escalabilidad en una plataforma de subastas en línea (LLOOGG): necesitaba guardar y recuperar sesiones de usuarios concurrentes muy rápido. Las alternativas de la época (como Memcached) solo guardaban cadenas simples, así que Sanfilippo construyó algo más potente.

### La idea clave: no es solo una caché

Memcached es un **almacén clave-valor de cadenas**: guardas un string, recuperas un string. Redis va mucho más allá: es un **servidor de estructuras de datos**. Además de strings, ofrece hashes, listas, conjuntos, conjuntos ordenados, bitmaps, HyperLogLog, streams, etc., y sobre todas ellas ofrece **operaciones atómicas de alto nivel** (incrementar un contador, añadir a un ranking, hacer *push*/*pop* de una cola) sin que la aplicación tenga que implementar esa lógica.

> **Por qué importa:** si solo necesitaras cachear cadenas, Memcached bastaría. Redis se elige cuando necesitas *estructuras* con semántica (colas, rankings, contadores atómicos, sets) sin montar esa lógica en tu aplicación ni pagar el coste de ir a una base de datos relacional para operaciones triviales.

### Atomicidad en Redis vs ACID (matiz importante para el examen)

En Redis, que un comando sea "atómico" significa que se ejecuta de principio a fin **sin que otro comando se intercale** — esto lo garantiza el hecho de que Redis usa un único hilo para procesar comandos. Pero esto **no es lo mismo que ACID**:

- `MULTI`/`EXEC` da atomicidad de lote ("todo o nada" en cuanto a que no se entrelazan comandos de otros clientes), pero **no aislamiento en el sentido SQL**: otro cliente puede leer estados intermedios entre comandos individuales *antes* de que se ejecute el `EXEC` (porque los comandos se van encolando, no ejecutando).
- Si necesitas aislamiento real tipo "leer-modificar-escribir sin que nadie más toque el dato mientras tanto", se usa `WATCH` + reintento (optimistic locking, ver sección 5.5).

### Redis vs Memcached

| Característica | Redis | Memcached |
|---|---|---|
| Estructuras de datos | Strings, Hashes, Lists, Sets, Sorted Sets, Bitmaps, HyperLogLog | Solo strings |
| Persistencia | RDB + AOF | No |
| Replicación | Sí (primary-replica) | No nativa |
| Transacciones | MULTI/EXEC | No |
| Publicación/Suscripción | Sí | No |
| Scripts Lua | Sí | No |
| Clúster | Sí (nativo) | Client-side sharding |

### Redis vs bases de datos relacionales (MySQL/MariaDB)

| Característica | Redis | MySQL / MariaDB |
|---|---|---|
| Almacenamiento | Memoria RAM | Disco (SSD/HDD) |
| Velocidad de lectura | ~0,1 ms | ~1–5 ms |
| Modelo de datos | Estructuras clave-valor | Tablas con esquema relacional |
| Transacciones | Multi/EXEC (atómicas, sin aislamiento SQL) | BEGIN/COMMIT/ROLLBACK (ACID) |
| Relaciones | No soporta JOINs | JOINs completos |
| Consistencia | Eventual (con réplicas) | ACID completa |
| Caso de uso principal | Caché, sesiones, colas | Datos persistentes, consultas complejas |

**¿Por qué Redis no soporta JOINs?** Porque cada clave es independiente: no existe el concepto de relación entre claves. Para "unir" datos de dos claves tendrías que leer ambas y combinarlas en la lógica de tu aplicación — Redis no gestiona ese cruce internamente.

**Consistencia eventual:** cuando escribes en el nodo primario y tienes réplicas, estas convergerán al mismo valor, pero no hay garantía de *cuándo* (aunque con replicación asíncrona el retraso típico es <1 ms). Para la mayoría de casos de uso (cachés, sesiones, contadores) esto es más que suficiente; para pagos o inventario crítico, se necesita consistencia fuerte (quórum), y ahí Redis no es la herramienta adecuada como fuente de verdad.

### Casos reales mencionados en las diapositivas

- **Twitter** usa Redis como capa de caché principal para timelines, procesando 40–100 millones de comandos por segundo.
- **GitHub** usa Redis para *rate limiting* de su API: un contador atómico por usuario (5.000 peticiones/hora) que se resetea solo gracias a `EXPIRE`.
- **Instagram** usa Redis con `INCR` para contadores de likes, con un patrón *Write-Behind* hacia Cassandra (escritura instantánea en Redis, persistencia asíncrona en Cassandra).

> **Concepto relacionado — Fan-out:** distribuir una actualización a múltiples destinatarios. *Fan-out on write*: cuando alguien publica, se escribe en la timeline de TODOS sus seguidores (lectura rápida, escritura lenta). *Fan-out on read*: al consultar tu timeline, se leen los posts de TODOS a quienes sigues (escritura rápida, lectura lenta). Es relevante porque Redis suele usarse justamente para acelerar el lado "lento" de este compromiso.

## 2. Características principales

### 2.1 Almacenamiento en memoria (RAM)

Todos los datos residen en RAM. Una operación de lectura/escritura en RAM tarda ~100 nanosegundos, frente a ~100 microsegundos en SSD: **1.000 veces más rápido**. La contrapartida es que la capacidad de Redis está limitada por la RAM disponible: un servidor con 64 GB de RAM puede almacenar como mucho ~64 GB de datos (menos el overhead del sistema). Para datasets más grandes se usa **Redis Cluster** (particionado entre varios nodos).

### 2.2 Persistencia opcional

A diferencia de Memcached (que pierde todo al reiniciar), Redis ofrece dos mecanismos de persistencia en disco:

| Mecanismo | Qué hace | Ventaja | Desventaja |
|---|---|---|---|
| **RDB** (Redis Database) | Snapshots periódicos del dataset completo en `dump.rdb` | Rápido, ficheros compactos, ideal para backups | Puede perder los datos escritos entre dos snapshots |
| **AOF** (Append Only File) | Log de todas las operaciones de escritura | Más seguro (con `appendfsync everysec`, como máximo 1s de pérdida) | Ficheros más grandes, algo más lento |
| **Híbrido (recomendado, Redis 4.0+)** | Combina RDB + AOF; el AOF se regenera periódicamente a partir del último snapshot RDB | Mejor de ambos mundos | Mayor complejidad de configuración |

> **Ejemplo de configuración típica en `redis.conf`:**
> ```conf
> save 900 1        # snapshot RDB si hay >=1 cambio en 900s
> save 300 10        # snapshot RDB si hay >=10 cambios en 300s
> appendonly yes     # activa AOF
> appendfsync everysec
> aof-use-rdb-preamble yes   # modo híbrido
> ```

### 2.3 Monohilo con E/S no bloqueante

Redis usa **un único hilo** para ejecutar comandos. Esto parece una limitación, pero es la clave de su diseño:

- **No necesita locks**: como solo un hilo ejecuta comandos, no hay condiciones de carrera ni deadlocks entre comandos.
- **E/S no bloqueante**: usa `epoll` (Linux), `kqueue` (macOS) o `IOCP` (Windows) para gestionar miles de conexiones simultáneas sin bloquearse esperando a cada una. Este patrón se llama **Reactor pattern**: un evento notifica al hilo cuando hay datos listos, y el hilo solo actúa cuando hay trabajo real que hacer (nada de *polling* activo).
- **Operaciones atómicas**: cada comando se ejecuta de forma indivisible, de principio a fin, sin interrupciones de otros comandos.

**Analogía del restaurante:** un solo camarero (el hilo de Redis) puede atender 100 mesas si cada pedido se resuelve en 100 nanosegundos. Añadir un segundo camarero introduciría complejidad de coordinación (locks) sin beneficio real, porque el cuello de botella no es la CPU sino la velocidad de cada operación individual.

**¿Por qué funciona con un solo hilo?** Si Redis usara E/S bloqueante, cada petición que tardase 1 ms en red bloquearía el hilo ese 1 ms entero, limitando el rendimiento a ~1.000 comandos/s. Con E/S no bloqueante, mientras un cliente espera su respuesta, el hilo sigue procesando comandos de otros clientes, alcanzando fácilmente >100.000 comandos/s.

### 2.4 Operaciones O(1) o O(log N)

Todas las operaciones de Redis tienen complejidad temporal garantizada y documentada:

| Operación | Complejidad | Significado |
|---|---|---|
| `SET` / `GET` | O(1) | Constante, no importa cuántas claves haya |
| `HSET` / `HGET` | O(1) | Acceso directo al campo de un hash |
| `LPUSH` / `RPUSH` | O(1) | Inserción por un extremo de la lista |
| `SADD` | O(1) | Inserción en hash table (set) |
| `ZADD` | O(log N) | Inserción en skip list (sorted set) |
| `LRANGE` | O(S+N) | Lineal: recorre la lista desde el offset S, N elementos |
| `HGETALL` | O(N) | Lineal: lee todos los campos del hash |

> **Consejo práctico:** usa `HGET` en lugar de `HGETALL` cuando solo necesites un campo. `HGETALL` es O(N) y puede bloquear el hilo único si el hash tiene millones de campos — recuerda que Redis es monohilo, así que un comando lento bloquea a *todos* los clientes durante su ejecución.

## 3. Arquitectura básica

### 3.1 Modelo cliente-servidor

Redis sigue un modelo **cliente-servidor** clásico: múltiples clientes se conectan por TCP (puerto por defecto `6379`) a un único servidor Redis. El servidor procesa los comandos de forma **secuencial** (monohilo) pero **no bloqueante**, lo que le permite gestionar miles de conexiones simultáneas.

Flujo de una petición:

1. El cliente envía un comando por TCP.
2. Redis lee el comando del buffer de red (sin bloquear).
3. Redis ejecuta el comando en memoria (~100 ns).
4. Redis escribe la respuesta en el buffer de red del cliente.
5. El cliente recibe la respuesta.

Ninguno de estos pasos bloquea el hilo principal: mientras un cliente espera su respuesta, Redis atiende a otros.

### 3.2 Protocolo RESP (REdis SERialization Protocol)

Redis se comunica con los clientes mediante **RESP**, un protocolo de texto simple, binario-seguro y fácil de implementar (por eso hay librerías cliente para casi cualquier lenguaje). Contenido considerado avanzado/opcional en la asignatura, pero útil para entender qué pasa "por debajo":

```
# Comando: PING
*2
$4
PING
# Respuesta:
+PONG

# Comando: SET mi_clave valor EX 60
*5
$3
SET
$7
mi_clave
$5
valor
$2
EX
$2
60
# Respuesta:
+OK

# Respuesta numérica (p.ej. de LLEN)
:42

# Respuesta de error (p.ej. GET sin argumentos)
-ERR wrong number of arguments for 'get' command
```

No es necesario memorizar la sintaxis exacta de RESP, pero sí entender la idea: cada tipo de respuesta tiene un prefijo (`+` éxito, `-` error, `:` entero, `$` string, `*` array), lo que hace que el protocolo sea rápido de parsear.

**Caso real — Instagram:** usa múltiples instancias Redis para contadores de likes y Stories, aprovechando la latencia consistente del modelo monohilo. Su arquitectura usa Redis como caché delante de Cassandra con un patrón *Write-Behind* (escritura instantánea en Redis, persistencia asíncrona en Cassandra).

## 4. Claves y valores

### 4.1 Convenciones de nombrado

Las claves en Redis son cadenas de texto. La convención más habitual sigue el patrón **`objeto:identificador:campo`**, separado por dos puntos (`:`):

| Parte Redis | Equivalente en SQL | Ejemplo | ¿Qué es? |
|---|---|---|---|
| Objeto | Tabla | `user` | El tipo de entidad que almacenas |
| Identificador | ID de fila (PRIMARY KEY) | `1000` | El registro concreto |
| Campo | Columna | `name` | La propiedad específica que guardas |

```bash
# Patrón: objeto:identificador:campo
SET user:1000:name "Juan García"
SET user:1000:email "juan@email.com"
SET session:abc123:userId "1000"
SET product:456:price "29.99"

# Patrón: un solo Hash agrupa todos los campos de una entidad (más eficiente)
HSET user:1000 name "Juan García"
HSET user:1000 email "juan@email.com"

# Patrón con namespaces (recomendado en producción)
SET app:shop:product:456:info "..."
SET app:shop:session:abc123:userId "1000"
```

**Equivalencia SQL vs Redis:**

```sql
-- SQL
SELECT name FROM user WHERE id = 1000
```
```bash
# Redis
GET user:1000:name
```

La fila `1000` de la tabla `user` con columna `name` en SQL equivale exactamente a la clave `user:1000:name` en Redis: objeto (`user`), identificador (`1000`), campo (`name`). La diferencia es que en Redis no hay un esquema formal — las claves son simplemente cadenas de texto que tú decides cómo estructurar.

### 4.2 TTL (Time To Live)

Cada clave puede tener un tiempo de vida en segundos. Al expirar, Redis la elimina automáticamente. Es la base de las cachés: guardas un dato con `TTL=3600` (1 hora) y, cuando caduca, lo recargas desde la fuente original.

### 4.3 Estructura interna, límites y buenas prácticas

Internamente, Redis almacena las claves en una **hash table global**. Cuando el número de claves/campos es pequeño, usa una estructura compacta (*listpack*); al crecer, hace *rehashing* incremental (de forma asíncrona, sin bloquear) a una hash table completa.

| Elemento | Límite máximo | Nota |
|---|---|---|
| Tamaño de clave | 512 MB | En la práctica, usar claves < 1 KB |
| Tamaño de valor | 512 MB | Strings: 512 MB. Listas: 2³²-1 elementos |
| Número de claves | Sin límite práctico | Depende de la RAM disponible |
| Niveles de anidamiento | Sin límite | Se recomienda < 6 niveles por rendimiento |
| Número de campos en hash | 2³²-1 (≈4 mil millones) | En la práctica, < 100.000 campos |

**Buenas prácticas de nombrado en producción:**

- Usa dos puntos (`:`) como separador: `user:1000:profile`.
- Evita espacios y caracteres especiales en claves.
- Usa namespaces (prefijo de aplicación): `app:shop:user:1000`.
- Sé consistente: si usas `user:1000:name`, no cambies a `users.1000.name` en otra parte del código.
- Evita claves demasiado largas: cada byte de clave consume memoria.
- **No uses `KEYS` en producción**: es O(N) y bloquea el servidor entero mientras se ejecuta (recuerda: monohilo). Usa `SCAN` en su lugar, que es iterativo y no bloqueante.

**Caso real — Discord:** usa claves con patrón `chat:{channel_id}` para particionar datos de chat entre múltiples instancias Redis, consiguiendo latencia < 1 ms y distribuyendo la carga de forma natural entre nodos del clúster.

## 5. Operaciones básicas

### 5.1 CRUD

```bash
# === CREATE — Crear / actualizar claves ===
SET user:1000 "Juan García"
SETEX session:abc123 1800 "userId:1000"   # Con TTL de 30 minutos
SETNX lock:resource1 "owner-123"          # Solo si no existe (lock)

# === READ — Leer claves ===
GET user:1000                             # Una clave
MGET user:1000 user:1001 user:1002        # Lectura múltiple (más eficiente)

# === UPDATE — Actualizar (sobrescribe) ===
SET user:1000 "Juan García Updated"

# === DELETE — Eliminar claves ===
DEL user:1000                             # Eliminación síncrona
UNLINK user:1001                          # Eliminación asíncrona (no bloqueante, Redis 4.0+)
```

**Diferencia clave:** en SQL, `INSERT` crea y `UPDATE` modifica, son operaciones distintas. En Redis, `SET` hace ambas cosas: si la clave ya existe la sobrescribe, si no existe la crea. No hay distinción entre crear y actualizar.

### 5.2 Equivalencia Redis vs SQL

| Operación | SQL (MariaDB) | Redis | Ejemplo Redis |
|---|---|---|---|
| Crear registro | `INSERT INTO users (...) VALUES (...)` | `SET` | `SET user:1000:name "Juan"` |
| Leer un registro | `SELECT name FROM users WHERE id=1000` | `GET` | `GET user:1000:name` |
| Leer varios registros | `SELECT ... WHERE id IN (...)` | `MGET` | `MGET user:1000:name user:1001:name` |
| Actualizar campo | `UPDATE users SET name=... WHERE id=1000` | `SET` | `SET user:1000:name "Juan García"` |
| Eliminar registro | `DELETE FROM users WHERE id=1000` | `DEL` | `DEL user:1000:name` |
| Verificar existencia | `SELECT COUNT(*) FROM users WHERE id=1000` | `EXISTS` | `EXISTS user:1000:name` |
| Incrementar contador | `UPDATE users SET views=views+1 WHERE id=1000` | `INCR` | `INCR user:1000:views` |
| Establecer expiración | (sin equivalente directo) | `EXPIRE` | `EXPIRE session:abc123 1800` |
| Listar todas las claves | `SHOW TABLES` | `SCAN` | `SCAN 0 MATCH user:* COUNT 100` |

### 5.3 Gestión de claves y metadatos

```bash
# Verificar existencia (devuelve número de claves que existen)
EXISTS user:1000              # 1 si existe, 0 si no
EXISTS user:1000 user:9999    # 1 (solo una existe)

# Obtener tipo de dato
TYPE user:1000                # "string", "hash", "list", "set", "zset"

# Obtener TTL (Time To Live)
TTL session:abc123            # -1 = sin expiración, -2 = no existe, >0 = segundos restantes
PTTL session:abc123           # TTL en milisegundos

# Buscar claves por patrón (¡CUIDADO en producción!)
KEYS user:*                       # O(N) — bloquea el servidor si hay millones de claves
SCAN 0 MATCH user:* COUNT 100     # Seguro e iterativo — recomendado

# Renombrar una clave
RENAME user:1000 user:1000:v2

# Obtener tamaño de una clave (en bytes)
MEMORY USAGE user:1000
```

### 5.4 Expiración de datos

```bash
# Establecer expiración en segundos
EXPIRE clave 600           # 10 minutos
PEXPIRE clave 1800000      # 30 minutos en milisegundos

# Establecer expiración con timestamp Unix
EXPIREAT clave 1726400000  # Expira en un timestamp específico

# Establecer valor CON expiración de una vez (atómico)
SETEX clave 600 "valor"    # SET + EXPIRE en una sola operación
SET clave "valor" EX 600   # Forma moderna (Redis 2.6.12+)
SET clave "valor" PX 1800000  # En milisegundos

# Eliminar expiración
PERSIST clave               # Quita el TTL, la clave ya no expira
```

### 5.5 Operaciones atómicas

```bash
# Incremento / decremento atómico (funciona con strings numéricos)
SET contador 0
INCR contador          # 1
INCR contador          # 2
INCRBY contador 5      # 7
DECR contador          # 6
DECRBY contador 3      # 3

# Incremento de punto flotante
SET precio 19.99
INCRBYFLOAT precio 0.5     # 20.49
INCRBYFLOAT precio -1.0    # 19.49

# Incrementar campo de un hash
HSET user:1000 login_count 0
HINCRBY user:1000 login_count 1
HINCRBY user:1000 login_count 1
```

**¿Por qué `INCR` es atómico?** Redis ejecuta todos los comandos en un único hilo. Mientras ejecuta `INCR`, nadie más puede ejecutar comandos hasta que termine. Esto garantiza que dos clientes concurrentes nunca obtienen el mismo resultado al incrementar el mismo contador — la misma propiedad que necesitan los bancos para contadores de transacciones.

### 5.6 Transacciones con MULTI/EXEC

```bash
# Iniciar transacción
MULTI

# Encolar comandos (NO se ejecutan aún)
SET user:1000:nombre "Juan"
SET user:1000:email "juan@email.com"
INCR estadisticas:usuarios

# Ejecutar todos los comandos de una vez
EXEC
# Respuesta:
# 1) OK
# 2) OK
# 3) (integer) 1

# Descartar transacción (si cambias de idea)
MULTI
SET temp "data"
DISCARD
```

**Diferencia con `INCR` suelto:** `MULTI`/`EXEC` garantiza que los comandos del lote se ejecutan de forma serial sin que se intercalen comandos de *otros* clientes, pero **no proporciona aislamiento** dentro del propio lote (no hay rollback parcial ni "ver antes/después" como en SQL). Si necesitas aislamiento real de tipo leer-modificar-escribir, usa `WATCH`.

### 5.7 Pipeline (agrupar comandos)

Si necesitas enviar múltiples comandos sin necesidad de que sean una transacción atómica, usa **pipeline**: agrupa comandos en un solo *roundtrip* a la red, reduciendo drásticamente la latencia.

```bash
# Sin pipeline: 3 roundtrips a la red
SET user:1:name "Juan"
SET user:1:email "juan@email.com"
SET user:1:age 28

# Con pipeline: 1 solo roundtrip
PIPELINE
SET user:1:name "Juan"
SET user:1:email "juan@email.com"
SET user:1:age 28
EXEC
```

```python
# En producción (pseudocódigo de la aplicación, con redis-py):
pipe = redis.pipeline()
for user in users:
    pipe.set(f"user:{user.id}:name", user.name)
pipe.execute()  # Un solo roundtrip para N comandos
```

**Impacto real:** sin pipeline, 1.000 comandos = 1.000 roundtrips (ida y vuelta por la red) ≈ 500 ms con una latencia de 0,5 ms por roundtrip. Con pipeline, 1.000 comandos = 1 roundtrip ≈ 0,5 ms. Mejora de ~1.000x. El cliente acumula los comandos en un buffer local y los envía todos juntos; Redis los ejecuta y devuelve todas las respuestas juntas.

> **Pipeline vs MULTI/EXEC:** Pipeline agrupa comandos para reducir latencia de red (optimización de rendimiento). MULTI/EXEC garantiza ejecución atómica sin interrupciones (garantía de consistencia). Son ortogonales: puedes combinar ambos si necesitas atomicidad **y** rendimiento a la vez.

### 5.8 WATCH (Optimistic Locking)

`WATCH` permite **optimistic locking**: monitoriza una o varias claves y aborta la transacción si alguna cambia entre el `WATCH` y el `EXEC`.

```bash
# Cliente 1: lee el saldo actual
WATCH cuenta:saldo
# Respuesta: (integer) 1000

# Mientras tanto, otro cliente modifica la clave:
# SET cuenta:saldo 800

# Cliente 1 intenta actualizar con el valor que leyó
MULTI
DECRBY cuenta:saldo 200
EXEC
# Respuesta: (nil)  <- la transacción se abortó porque la clave cambió

# Cliente 1 debe reintentar:
WATCH cuenta:saldo
# Leer nuevo valor: 800
MULTI
DECRBY cuenta:saldo 200
EXEC
# Respuesta: (integer) 1  <- ahora sí se ejecuta
```

**Pesimista vs optimista:**

- **Pesimista** (`SELECT ... FOR UPDATE` en SQL): bloquea la fila ANTES de leer. Otros esperan. Útil cuando los conflictos son frecuentes.
- **Optimista** (`WATCH`): no bloquea nada. Al escribir, verifica que el valor no cambió; si cambió, reintenta (*retry*). Útil cuando los conflictos son infrecuentes — evita el coste de bloquear cuando normalmente no hace falta.

Flujo general: `WATCH clave → Leer valor → MULTI → Encolar comandos → EXEC → (OK: hecho) | (nil: clave modificada → volver a WATCH)`.

**Caso real — Transferencia bancaria:** `WATCH balance_cuenta_A`, leer saldo, verificar que es suficiente, `MULTI`, `DEBITO A`, `CREDITO B`, `EXEC`. Si otro proceso modificó el saldo entre el `WATCH` y el `EXEC`, la transacción falla y hay que reintentar — evitando así una transferencia basada en datos obsoletos.

**Caso real — Netflix:** usa `EXPIRE` en sesiones de reproducción para limpiar automáticamente datos transitorios tras cada sesión: cuando un usuario cierra la app, su sesión expira a los 30 minutos, liberando memoria sin necesidad de un proceso de limpieza externo.

## 6. Casos de uso fundamentales

Redis se usa típicamente para: caché de consultas, gestión de sesiones, contadores y rankings, colas de mensajes, rate limiting, datos geoespaciales, Pub/Sub y locks distribuidos.

### 6.1 Caché de consultas (el caso más común)

Redis almacena resultados de consultas frecuentes (productos, perfiles, configuraciones) para evitar golpear la base de datos principal en cada petición.

```bash
# Consulta frecuente: información de producto
# Sin caché: SELECT * FROM products WHERE id=456 (5ms en MariaDB)
# Con caché: GET product:456:info (0.1ms en Redis)

SET product:456:info '{"name":"iPhone 15","price":999,"stock":50}' EX 300
GET product:456:info

# Cuando el producto se actualiza, invalidar la caché
# UPDATE products SET price=899 WHERE id=456;
DEL product:456:info
```

### 6.2 Gestión de sesiones

Redis es ideal para sesiones de usuario porque permite acceso rápido y expiración automática (no necesitas un job de limpieza aparte).

```bash
# Login: crear sesión
SET session:xyz789:userId "1000" EX 1800
SET session:xyz789:role "admin" EX 1800
SET session:xyz789:lastAccess "2026-09-15T10:30:00" EX 1800

# Verificar sesión en cada petición
GET session:xyz789:userId

# Renovar sesión (sliding expiration)
EXPIRE session:xyz789:userId 1800

# Logout: eliminar sesión
DEL session:xyz789:userId
DEL session:xyz789:role
DEL session:xyz789:lastAccess
```

### 6.3 Contadores y rankings

Las operaciones `INCR` y los Sorted Sets son perfectos para métricas en tiempo real.

```bash
# Contador de vistas de producto
INCR views:product:456
INCR views:product:456
INCR views:product:456    # 3 vistas

# Contador de likes
INCR likes:post:789

# Ranking de productos más vendidos
ZADD top:sales 150 "product:456"
ZADD top:sales 230 "product:789"
ZADD top:sales 89 "product:123"
ZREVRANGE top:sales 0 2 WITHSCORES   # Top 3
```

### 6.4 Colas de mensajes

Redis puede usarse como cola de mensajes simple con `LPUSH` + `BRPOP` (el `B` inicial de `BRPOP` indica que es *blocking*: el consumidor espera hasta que haya una tarea, en vez de hacer *polling*).

```bash
# Productor: añadir tareas
LPUSH cola:tareas '{"task":"send_email","to":"user@email.com"}'
LPUSH cola:tareas '{"task":"process_image","id":456}'

# Consumidor: extraer tareas (bloqueante)
BRPOP cola:tareas 0    # Espera hasta que haya una tarea

# Si necesitas colas con prioridad:
LPUSH cola:alta '{"priority":"high","task":"..."}'
LPUSH cola:baja '{"priority":"low","task":"..."}'
```

### 6.5 Rate limiting

Controlar la tasa de peticiones de un cliente para evitar abusos.

```bash
# Rate limiting con ventana fija (100 peticiones/hora)
SET ratelimit:user:1000 0 EX 3600    # Contador con TTL de 1 hora

# En cada petición:
INCR ratelimit:user:1000
# Si el resultado > 100 -> rechazar petición (HTTP 429)
```

**Caso real — Twitch:** usa Redis para caché de chat en tiempo real, gestionando millones de mensajes por minuto. Durante *Twitch Plays Pokémon*, el sistema recibió 1,2 millones de mensajes en 24 horas y una sola instancia Redis no daba abasto. La solución fue hacer *shard* por canal de chat (`chat:{channel_id}`), distribuyendo la carga entre múltiples instancias Redis.

## 7. Cuándo NO usar Redis

Un buen ingeniero sabe reconocer los límites de sus herramientas. Redis es excelente para lo que está diseñado, pero **no es la solución para todo**:

| Limitación | Explicación | Alternativa |
|---|---|---|
| Coste de RAM | ~1 €/GB en RAM vs ~0,1 €/GB en SSD. 100 GB en Redis cuesta ~100 €/mes vs ~10 €/mes en disco | Caché selectiva: solo datos "calientes" en Redis |
| Sin consultas complejas | No soporta JOINs, GROUP BY, subqueries | Redis para caché + MariaDB/PostgreSQL para consultas |
| Límite de 512 MB por valor | Un string, hash o lista no puede superar 512 MB | Particionar datos en múltiples claves |
| Persistencia no ACID | RDB puede perder datos entre snapshots; AOF es mejor pero no garantiza consistencia como una BD relacional | Usar Redis como caché, no como fuente primaria de datos |
| Monohilo en escritura | Las escrituras secuenciales están limitadas por un solo hilo | Para escritura masiva, considerar Kafka o BD por columnas |
| No reemplaza una BD relacional | No tiene transacciones ACID completas, ni relaciones, ni DDL | Usar Redis como complemento, no como sustituto |

> **Regla de oro:** Redis es un **complemento** de tu base de datos principal, no un **sustituto**. Úsalo para caché, sesiones, contadores y colas. Deja la persistencia fuerte y las consultas complejas a la BD relacional (o a otra BD especializada, según T6/T7 de la asignatura).

### Caso real: Twitch Plays Pokémon (2016) — cuando Redis se satura

- **Problema:** 1,2 millones de mensajes de chat en 24 horas; CPU de Redis al 100% (single-threaded, un solo núcleo saturado); 3.021 conexiones activas, 2.311 en espera; una sola instancia Redis para todo el chat.
- **Solución:** *shard* por clave (`chat:{channel_id}` → cada canal va a una instancia Redis diferente), HAProxy para balanceo de carga entre particiones, y reducción de conexiones en espera innecesarias.
- **Lección:** Redis es single-threaded por diseño. Cuando un solo nodo se satura, la solución no es "optimizar el código" sino **particionar los datos** en múltiples instancias — que es justo lo que resuelve Redis Cluster.

## 8. Alternativas a Redis

Desde 2024, Redis Ltd. cambió la licencia de Redis (de BSD a **RSALv2/SSPL**), lo cual no afecta a Redis como herramienta técnica, pero sí a quién puede ofrecerlo como servicio gestionado sin pagar licencia. Esto provocó la aparición de **Valkey**, un *fork* mantenido por la Linux Foundation.

| Solución | Arquitectura | Licencia | Rendimiento (8 cores) | Cuándo usarla |
|---|---|---|---|---|
| **Redis 8** | Single-thread + bg helpers | RSAL/SSPL/AGPL | ~250K ops/s | Estándar de facto, máximo ecosistema |
| **Valkey 8** | Single-thread + I/O async | BSD-3 (Linux Foundation) | ~700K ops/s | Reemplazo directo, open source, soportado por AWS/GCP |
| **Dragonfly** | Shared-nothing por core | BSL 1.1 → Apache 2.0 | ~3,8M ops/s | Máximo rendimiento, 80% menos memoria |
| **KeyDB** | Multi-threaded fork | BSD-3 | ~1M ops/s | Replicación multi-master, FLASH tiering |
| **Memcached** | Multi-threaded, simple KV | BSD revisado | Muy alto (simple) | Solo caché simple sin estructuras de datos |
| **Garnet (Microsoft)** | C# async, RESP-compatible | MIT | ~2,5M ops/s | Ecosistema .NET, compatibilidad Redis |

**Concepto clave:** la compatibilidad entre Redis, Valkey, Dragonfly y KeyDB es casi total — todos hablan el mismo protocolo (RESP). Cambiar de uno a otro suele ser un cambio de configuración, no de código de aplicación. Lo que cambia entre ellos es la licencia, el rendimiento de un solo nodo, y el soporte de módulos propios de Redis.

**¿Qué elegir?** Para la mayoría de proyectos: **Valkey** (open source, compatible al 100% con Redis, soportado por AWS/GCP). Para máximo rendimiento de un solo nodo: **Dragonfly**. Para caché pura sin estructuras: **Memcached**. Redis sigue siendo el estándar de facto por su ecosistema y documentación.

Desde finales de 2024, AWS ElastiCache usa Valkey por defecto para nuevos despliegues, y Google Cloud MemoryStore migró a Valkey en 2025 — es muy probable que, si despliegas en la nube hoy, ya estés usando Valkey sin saberlo.

## 9. Buenas prácticas al ponerlo en práctica

- Empieza siempre con `redis-cli ping` para verificar la conexión antes de cualquier operación.
- Usa `CONFIG GET *` para ver toda la configuración actual y familiarizarte con las opciones disponibles.
- En producción, **nunca uses `KEYS *`** — usa `SCAN` con cursor para iterar claves sin bloquear el servidor.
- Configura `maxmemory` y `maxmemory-policy` desde el primer día para evitar errores inesperados cuando la RAM se llene.
- Monitoriza con `INFO stats` periódicamente para detectar problemas antes de que afecten a los usuarios.

## 10. Resumen / puntos clave (repaso rápido)

- Redis = servidor de **estructuras de datos** en memoria, no solo una caché de strings (eso es Memcached).
- "Atómico" en Redis significa ejecución sin interrupciones (garantizado por el hilo único), **no** es lo mismo que ACID/aislamiento SQL.
- Modelo **monohilo + E/S no bloqueante** (epoll/kqueue/IOCP, patrón Reactor): elimina locks y deadlocks, y permite >100.000 comandos/s.
- Todas las operaciones tienen complejidad garantizada: la mayoría O(1), algunas O(log N) (`ZADD`), evita las O(N) en producción (`HGETALL`, `KEYS`) sobre datasets grandes.
- Persistencia **opcional**: RDB (snapshots), AOF (log de escrituras), o híbrido (recomendado).
- Convención de claves: `objeto:identificador:campo`, con namespaces de aplicación (`app:shop:...`).
- TTL con `EXPIRE`/`EXPIREAT`/`SETEX`/`SET ... EX` — base de cachés y sesiones autolimpiables.
- `MULTI`/`EXEC` = atomicidad de lote sin aislamiento; `pipeline` = reduce roundtrips de red (rendimiento, no atomicidad); `WATCH` = optimistic locking para leer-modificar-escribir seguro.
- En producción: `SCAN` en vez de `KEYS`, `UNLINK` en vez de `DEL` para borrados grandes, configurar `maxmemory`.
- Casos de uso típicos: caché de consultas, sesiones, contadores/rankings (Sorted Sets), colas (`LPUSH`+`BRPOP`), rate limiting.
- Redis **no** reemplaza una BD relacional: sin JOINs, límite de 512 MB por valor, persistencia no-ACID, coste de RAM elevado. Es un complemento, no un sustituto.
- El cambio de licencia de Redis (2024, RSAL/SSPL) impulsó **Valkey** (fork open source de la Linux Foundation) como alternativa directa; también existen Dragonfly, KeyDB, Garnet — todos compatibles con el protocolo RESP.

## 11. Preguntas de autoevaluación

**1. ¿Por qué Redis se considera un "servidor de estructuras de datos" y no simplemente una caché?**
> Porque, además de strings, ofrece hashes, listas, sets, sorted sets, bitmaps, HyperLogLog, etc., todos con operaciones atómicas de alto nivel (incrementar, hacer push/pop, añadir a un ranking) que la aplicación no tiene que reimplementar. Memcached, en cambio, solo almacena cadenas.

**2. ¿`MULTI`/`EXEC` en Redis ofrece las mismas garantías que una transacción SQL con aislamiento?**
> No. Garantiza que los comandos del lote se ejecutan de forma serial sin que se intercalen comandos de otros clientes (atomicidad de lote), pero no ofrece aislamiento real: otro cliente puede ver estados intermedios entre operaciones de una transacción antes de que se llame a `EXEC`. Para aislamiento real se usa `WATCH` + reintento.

**3. ¿Por qué el diseño monohilo de Redis no es un cuello de botella en la mayoría de los casos?**
> Porque cada operación tarda del orden de nanosegundos (todo en RAM) y la E/S de red es no bloqueante (epoll/kqueue/IOCP). Mientras un cliente espera su respuesta, el hilo sigue procesando comandos de otros clientes, alcanzando cientos de miles de comandos por segundo sin necesitar locks entre hilos.

**4. Un contador de "likes" implementado con `INCR` se pierde si Redis cae sin persistencia. ¿Por qué empresas como Instagram lo usan igualmente en producción?**
> Porque `INCR` es atómico y O(1), lo que evita condiciones de carrera entre usuarios concurrentes, y porque el patrón Write-Behind persiste el dato de forma asíncrona en una base de datos duradera (p. ej. Cassandra). El riesgo de perder unos segundos de likes es aceptable frente al beneficio de latencia; para datos donde eso no sea aceptable (saldo bancario), no se usaría este patrón sin más garantías.

**5. Diferencia entre RDB y AOF como mecanismos de persistencia.**
> RDB hace snapshots periódicos del dataset completo (rápido, compacto, pero puede perder cambios entre snapshots). AOF registra cada operación de escritura en un log (más seguro, como máximo ~1s de pérdida con `appendfsync everysec`, pero genera ficheros más grandes). El modo híbrido combina ambos.

**6. ¿Por qué no se deben hacer JOINs en Redis?**
> Porque cada clave es independiente; no existe ningún mecanismo interno de relación entre claves. Para "unir" datos habría que leer múltiples claves y combinarlas en la lógica de la aplicación, algo que Redis no gestiona de forma nativa.

**7. Explica la diferencia entre `KEYS` y `SCAN`, y por qué importa en producción.**
> `KEYS` tiene complejidad O(N) y bloquea el hilo único de Redis durante toda la búsqueda, congelando el servidor para todos los clientes si hay millones de claves. `SCAN` es iterativo (usa un cursor) y no bloquea el servidor, aunque tarda varias llamadas en completarse. En producción siempre se prefiere `SCAN`.

**8. ¿Qué es el optimistic locking con `WATCH` y cuándo se prefiere sobre un lock pesimista?**
> `WATCH` monitoriza una clave; si cambia entre `WATCH` y `EXEC`, la transacción se aborta (devuelve `nil`) y hay que reintentar. Se prefiere sobre un lock pesimista (`SELECT ... FOR UPDATE`) cuando los conflictos de concurrencia son poco frecuentes, ya que evita el coste de bloquear recursos innecesariamente.

**9. ¿Qué diferencia hay entre `pipeline` y `MULTI`/`EXEC`?**
> Pipeline es una optimización de red: agrupa varios comandos en un único roundtrip TCP para reducir latencia, pero no garantiza atomicidad (otros clientes pueden intercalar comandos). `MULTI`/`EXEC` garantiza que los comandos del bloque se ejecuten sin interrupciones de otros clientes, pero no reduce necesariamente el número de roundtrips por sí solo. Pueden combinarse.

**10. ¿Qué llevó a la creación de Valkey y qué implica para un desarrollador que ya usa Redis?**
> En marzo de 2024, Redis Ltd. cambió la licencia de Redis de BSD a RSALv2/SSPL, lo que restringe cómo terceros pueden ofrecer Redis como servicio gestionado. Esto motivó la creación de Valkey, un fork mantenido por la Linux Foundation bajo licencia BSD-3, totalmente compatible con el protocolo RESP. Para un desarrollador, migrar de Redis a Valkey suele ser un cambio de configuración (endpoint/imagen), no de código.

**11. Da un ejemplo de cuándo Redis NO sería la herramienta adecuada.**
> Por ejemplo, como base de datos principal de un sistema de facturación que necesita transacciones ACID completas, relaciones entre tablas (clientes, pedidos, facturas) y consultas complejas con JOINs y agregaciones — ahí una base de datos relacional (MySQL/PostgreSQL) es la opción correcta; Redis podría usarse como caché complementaria, no como fuente de verdad.

**12. ¿Qué significa que Redis tenga "consistencia eventual" con réplicas, y en qué casos no es suficiente?**
> Significa que tras una escritura en el nodo primario, las réplicas convergerán al mismo valor pero sin garantía exacta de cuándo (aunque típicamente en <1 ms con replicación asíncrona). Es suficiente para cachés, sesiones o contadores, pero no para casos como pagos o control de inventario crítico, donde se necesita consistencia fuerte (por quórum), algo que Redis estándar no ofrece de forma nativa.

**13. ¿Por qué se recomienda usar `HGET` en lugar de `HGETALL` cuando solo se necesita un campo de un hash?**
> Porque `HGET` es O(1) (acceso directo al campo), mientras que `HGETALL` es O(N) y recorre todos los campos del hash. Si el hash tiene millones de campos, `HGETALL` puede bloquear el hilo único de Redis durante un tiempo considerable, afectando a todos los clientes conectados.

**14. Explica el patrón de rate limiting mostrado en las diapositivas usando `INCR` y `EXPIRE`/`EX`.**
> Se crea una clave por usuario con un contador inicializado a 0 y un TTL igual a la ventana de tiempo deseada (p. ej. `EX 3600` para una hora). En cada petición se ejecuta `INCR` sobre esa clave; si el valor devuelto supera el límite permitido, se rechaza la petición (HTTP 429). Al expirar el TTL, el contador se reinicia automáticamente sin necesidad de un proceso de limpieza.

**15. ¿Qué lección deja el caso de Twitch Plays Pokémon sobre la escalabilidad de Redis?**
> Que al ser single-threaded por diseño, una sola instancia Redis tiene un límite de CPU claro (un núcleo). Cuando ese límite se alcanza, la solución no es optimizar el código de la aplicación sino particionar los datos (sharding) entre múltiples instancias Redis según una clave de partición adecuada (p. ej. por canal de chat) — que es exactamente el problema que resuelve Redis Cluster de forma nativa.
